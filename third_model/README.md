## 처음 받는 사람: 이 폴더 하나만 있으면 됩니다
1. **Python 3.9 이상** 설치 (python.org)
2. 이 폴더(`third_model`)를 VS Code로 열기 → `실행 및 디버그` → **`1. 환경 설치`** (또는 `python 실행/1_환경설치.py`)
   → `.venv` 가상환경을 만들고 `requirements.txt` 패키지를 설치 (PyTorch는 필요 없음)
3. 팀 실측 폴더 4개를 `data/` 아래에 폴더째로 넣기 ([data/README.md](data/README.md))
4. 가상 성능 시험: `실행 및 디버그` → **`가상 성능 시험`** (약 15분, 빠른 확인은 약 3분) 또는

   ```
   python 가상테스트/성능시험.py --g3 "data/정상 데이터_공3옥상" --g3 "data/정상 데이터_공3옥상(11.16)" --yg "data/정상 데이터_욧골(11.15)" --fault "data/고장 데이터_욧골" --test-scale 2.0 --jobs 8
   ```

   결과: `가상테스트_결과/성능시험/결과.json` + 화면 표. 가상 로봇은 실측 기록을 재료로 실행할 때 새로 만듦
5. 실측 6분 이상 기록이 있으면: `python run.py check` → `python run.py train` → `python run.py diagnose`


## 11/19 최종: AI 2개 (주파수 모양 오토인코더 + 랜덤포레스트)

```
센서 기록 → 1초씩 자르기 (로봇마다 처음 5분 = 평소)
  ├─ 특징 101개: 진동 18 · 바퀴 11 · 주파수 모양 72 (축마다 2~235 Hz 24칸의 에너지 비율)
  │    ├→ ① 주파수 모양 오토인코더 (비지도, 정상만 학습) + 바퀴 점수(규칙) → 처음 보는 고장
  │    └→ ② 랜덤포레스트 (지도, 고장 라벨 + 가상 이상) → 아는 고장 · 처음 보는 이상
  │         → 둘 중 큰 값 = 건강 점수 → 1분 점수(중앙값)가 2.0점 이상이면 주의, 6점 이상 경고
  │    └→ 원인: 같은 랜덤포레스트가 '종류|바퀴' 또는 '처음 보는 이상' 확률 + SHAP 근거 (확률 60% 미만 = 원인 미확정)
  └─ 전류 · 전압: AI 없이 평소와 비교 (전류 높음 · 배터리 낮음 · 사용량)
```

**고친 오류:** 팀 기록의 enc2(샘플마다 센 펄스)에 가끔 튀는 값(359 등)이 있으면 '속도'로 잘못 읽었음 (`dataio._encoder_kind`, 최댓값 → 99% 지점)

**바꾼 것**
- 주파수 모양 특징 (`SPEC_FEATURES`, `SPEC_BANDS = 24`): 그 칸 에너지 ÷ 전체 에너지(로그). 바닥이 거칠어지면 모든 칸이 함께 커져 비율은 그대로,
  기어·베어링 고장은 특정 칸만 커져 비율이 바뀜 → 바닥 바뀜 오경보는 적고 처음 보는 고장은 잘 드러남
- 주파수 모양 오토인코더 (`SPEC_AE`, 72 → 32 → 8 → 32 → 72, 정상만 학습)
- 랜덤포레스트 하나로 감지 + 원인 (`RF_DETECTOR`, `CAUSE_MODEL = "rf_shared"`). 1D-CNN은 끔 (`DEEP_MODEL = False`, 켜면 예전 1D-CNN 구성)
- 가상 이상 (`SYNTH_ANOMALY`, `pipeline/augment.py`): 학습용 정상 로봇 진동에 무작위 좁은 대역 잡음 · 순음 · 주기 충격,
  바퀴가 돌 때는 절반을 '바퀴 회전 × k배 순음(k = 1~80)' · '1회전에 m번 충격(m = 1~4)'으로 넣은 복사본을 '처음 보는 이상' 라벨로 함께 학습 (데이터 파일은 바꾸지 않음)
- 판정: `PERIOD_QUANTILE = 0.75`, `CONFIRM_PERIODS = 1`, 주의 경보 `CAUTION_ALARM = 2.5` (눈금 3점 = 정상 99.5%는 그대로) — 검증 로봇으로 고름

**가상 시험** (`가상테스트/성능시험.py --test-scale 2.0`, 약 15분: 실측 정상 조각 + 실측 테이프 고장 증가분으로 만든 가상 로봇, 엔코더 4개 가정, 각속도 없음, 엔코더 끊김 없음.
판정 설정과 '원인 미확정' 기준은 아는 고장만 있는 검증 로봇으로 고르고, 처음 보는 시험 로봇 약 170대씩으로 잼. **실측 성능이 아님**)

| 시험 (약 170대씩, 11/20 최종) | 정답률 | 아는 고장 감지 | 처음 보는 고장 감지 | 오경보 | 원인 맞음 |
|---|---|---|---|---|---|
| 아는 고장만 | 97.0% | 96.6% | – | 2.5% | 100% |
| 고장 절반이 처음 보는 고장 (기본 세기) | **96.4%** | 94.9% | 92.3% (48/52) | **0%** | **97.6%** |
| 충분히 진행된 고장(세기 ×1.2~1.5) + 절반이 처음 보는 고장 | 97.0% | 97.4% | 95.6% (43/45) | 2.4% | 90.0% |
| 고장 세기 무작위(×0.4~1.0) + 절반이 처음 보는 고장 (현실 조건) | 92.8% | 90.0% | 82.9% (34/41) | 0% | 100% |

11/20에 바뀐 것: 엔코더로 계산한 gz(회전 속도) 진동 특징 6개, 주파수 '뾰족함' 3개(`SPEC_PEAK`) → 특징 110개.
원인은 점수가 주의 문턱 이상인 1초 창만으로(`CAUSE_HIGH_ONLY`), 종류 먼저(`CAUSE_BY_KIND`), 최근 3분(`CAUSE_WINDOW = 180`), 확신 0.35 미만이면 미확정(`UNKNOWN_PROB`, 검증으로 고름).
판정은 검증 로봇으로 고른 1분 점수 중앙값 · 1번 · 주의 2.0점. 남은 약점: 간헐 고장 · 바퀴 찍힘(약하면 놓침, 강하면 '체결 풀림'으로 봄) · 기어 마모를 '마찰'로 보는 경우 2대

- 처음 보는 고장 = 기어 마모(기어 맞물림 순음, 바퀴 회전 × 48) · 바퀴 찍힘(1회전에 한 번 충격) · 학습에 없던 주파수(120 · 160 Hz)의 베어링. 학습 로봇에는 없음.
  현실 조건에서 종류별: 기어 마모 7/9 · 바퀴 찍힘 7/11 · 새 주파수 베어링 13/13 (바퀴 찍힘이 가장 어려움)
- 앞서 26대 시험에서 처음 보는 고장 100%가 나왔지만, 로봇을 늘리고 고장 세기를 섞자 83~96%로 내려감 → 작은 시험의 100%는 우연이 컸음.
  네 지표(정답률 · 아는 고장 · 처음 보는 고장 · 원인)가 모두 95% 이상인 조건은 아직 없음 (기본 세기에서 처음 보는 고장 94.2%, 원인 92.0%)
- 가상 이상의 '바퀴 회전에 묶인 순음 · 충격'은 시험의 기어 · 찍힘과 같은 계열의 모양이라, 처음 보는 고장 점수가 실제보다 좋게 나올 수 있음.
  원인 맞음: 아는 고장은 종류, 처음 보는 고장은 '처음 보는 이상'(베어링은 '마찰 증가'도 맞음)으로 셈
- 1D-CNN 구성(11/19 오후)은 처음 보는 고장 87%를 잡았지만 바닥이 바뀐 정상 로봇에 오경보 21~28%라 기본에서 뺌

## third_model에서 바뀐 점

```
센서 값(진동·바퀴 속도) → ② 고장인가? (특징 오토인코더 + 1D-CNN 오토인코더, 큰 값)
                         → 이상이면 ③ 무슨 고장? (1D-CNN 원인 분류, 파형 + 특징)
                         → 확률 1위가 60% 미만이면 '원인 미확정 (학습에 없는 이상일 수 있음)'
```

- **새로 필요한 것: PyTorch** (CPU판으로 충분)
  `pip install torch --index-url https://download.pytorch.org/whl/cpu`
- **실행 순서는 그대로**: `python run.py check` → `python run.py train` → `python run.py diagnose --path 시연폴더`
- 1D-CNN 입력: 1초 파형 (ax, ay, az + 학습에 쓴 엔코더의 바퀴 속도) × 512칸, 로봇마다 처음 5분 기준으로 정규화
- 교차검증 비교표에 `1D-CNN 오토인코더 (파형)`, `특징 AI + 1D-CNN (주 모델)`이 함께 나옵니다
- 판단 근거: 1D-CNN은 SHAP 대신 '입력 × 기울기'로 "X축 가속도 파형 0.2~0.4초"처럼 어느 축·어느 시점을 봤는지 보여 줍니다
- 설정 (`config.py` 맨 아래 '딥러닝' 부분)
  - `DEEP_MODEL = False` → 예전 방식(특징 + 오토인코더 + 랜덤포레스트)으로 돌아감 (PyTorch 없이 실행 가능)
  - `DEEP_MAIN = "cnn_ae"` → 건강 점수를 1D-CNN만으로
  - `CAUSE_MODEL = "rf"` → 원인 분류를 랜덤포레스트로
  - `DEEP_EPOCHS`, `DEEP_BATCH`, `DEEP_LR` → 학습 설정 / `UNKNOWN_PROB` → 원인 미확정 기준
- 학습 시간: 교차검증 겹마다 1D-CNN 두 개를 새로 학습하므로 second_model보다 오래 걸립니다 (CPU 기준 데이터 양에 따라 수 분~수십 분). 빨리 보려면 `python run.py train --no-eval`
- 이전 변경 내역: `변경사항_이전.md`

## 1. 한눈에 보기

배송로봇(AMR)의 진동·바퀴 속도를 보고 **고장이 났는지, 무슨 고장인지(어느 바퀴)** 알려 줍니다.
전류·전압은 AI와 따로 **감시용**(전류 높음, 배터리 낮음, 사용량 mAh)으로만 씁니다.

```
CSV (시간, 가속도·각속도 6축, 엔코더 4개, 모터 명령, 전류, 전압, 라벨)
 │
 ├─ AI (학습)
 │    1초 창 → 특징 47개 (진동 36 + 바퀴 11) → 로봇마다 '평소'와 비교한 z값
 │      ├→ 오토인코더 점수 ┐
 │      └→ 바퀴 이상 점수 ┴→ 큰 쪽 = 건강 점수 (3 주의 · 6 경고 · 9 정지 위험)
 │                           → 1분마다 상태 판정 (2번 연속일 때만 바뀜)
 │      └→ 랜덤포레스트: 고장 종류 + 바퀴, SHAP: 판단 근거 3개
 │
 └─ 감시 (학습 없음): 전류가 평소(처음 5분)보다 높음 · 배터리 7.0 V 아래 · 사용량 mAh
```

## 3. 수집해야 할 데이터

### 3-1. CSV 열 (한 줄 = 샘플 하나, 약 500 Hz)

| 열 | 필수 | 알아듣는 이름·단위 (자동 변환) |
|---|---|---|
| 시간 | ✅ | `time`(초), `시간`, `t_us`·`micros`(µs), `t_ms`(ms), `시간(us)` 등 |
| 가속도 3축 | ✅ | `ax, ay, az` — g 또는 센서 원래 정수값(÷8192) |
| **각속도 3축** | ✅ | `gx, gy, gz` — °/s 또는 원래값(÷65.5). **없으면 학습·진단 불가** |
| 엔코더 4개 | 권장 | `enc1~enc4`, `엔코더1~4`, `enc_fl…` — 누적 펄스 / 샘플마다 센 펄스 / 속도 자동 판단. 1 앞왼 · 2 앞오른 · 3 뒤왼 · 4 뒤오른 |
| 모터 명령 | 권장 | `cmd`, `pwm`, `spd`, `모터명령` |
| 전류, 전압 | 권장 | `mA`, `mV`, `전류(mA)`, `current`, `voltage` (감시용) |
| 로봇 이름 | 권장 | `robot` — 같은 이름의 파일은 이어 붙임. 없으면 파일 이름이 로봇 이름 |
| 고장 라벨 | 고장 기록에 | `label`/`fault_kind`(normal·idle, unbalance, looseness, bearing), `fault_wheel`(fl·fr·rl·rr), `fault_severity`(0~1) |
| 구간 | 선택 | `segment` — 장소·노면 이름 (바닥이 바뀌는 곳 구분) |

### 3-2. 기록 목록 (최소 권장)

| 기록 | 개수 | 길이 | 방법 |
|---|---|---|---|
| **정상** | **3개 이상 (많을수록 좋음)** | 10분 이상 | 다른 날·바닥·짐·배터리 A/B·속도로. **실측 성능에 가장 큰 영향** |
| 고장: 불평형 | 2개 이상 | 15분 이상 | 처음 5분은 고장 없이 → 고장을 내고 계속 기록 |
| 고장: 체결부 풀림 | 2개 이상 | 15분 이상 | 같은 방식. 어느 바퀴인지 `fault_wheel`에 |
| 고장: 베어링 결함 | 2개 이상 | 15분 이상 | 같은 방식 |
| 시연용 | 1~2개 | 10분 이상 | **처음부터 따로 보관**, 마지막에 한 번만 진단 |

기록 규칙:
- 한 기록은 **6분 이상** (처음 5분 = 그 로봇의 '평소' 기준, 판정하지 않음). 처음 5분에 전진·정지·회전·후진을 섞을 것
- 정상과 고장 기록은 **같은 날·같은 바닥·비슷한 길이**로 (다르면 그 차이를 고장으로 배움)
- 센서 붙인 자세를 바꾸지 말 것 (바꿨으면 새 로봇 이름으로 기준을 다시)
- 엔코더 4개가 **모든 기록에** 있어야 바퀴 특징이 켜짐

| 설정 | 값 | 뜻 |
|---|---|---|
| `ENCODER_FEATURES` | "auto" | 모든 학습 기록에 엔코더 4개가 살아 있으면 바퀴 특징 11개 사용 |
| `WHEEL_SCORE` | True | 바퀴 이상 점수(한 바퀴만 튀는 정도)를 오토인코더 점수와 함께 사용 |
| `CAL_SPLIT` | "tail" | 3점 눈금을 정하는 정상 로봇 = 이름순 뒤쪽 1/3 → **고장 감지 우선** |
| `AE_ENSEMBLE` | 1 | 오토인코더 개수 |
| `SPIKE_K` | 0 (끔) | 센서 읽기 오류(샘플 하나만 튀는 값) 빼기 |
| `PERIOD_S` / `PERIOD_QUANTILE` / `CONFIRM_PERIODS` | 60 / 0.5 / 2 | 1분마다, 1초 점수의 중앙값으로, 2번 연속일 때 상태 변경 |
| `BASELINE_PERIODS` | 5 | 처음 5분 = 정상 기준 |
| `THRESH` | 3 / 6 / 9 | 주의 / 경고 / 정지 위험 점수 |
| `HEARTBEAT_S` | 300 | 실행 중 '학습 중'·'평가 중'을 다시 알리는 간격[초] (시작할 때는 바로 한 번) |

### 5-3. 실측에서 성능이 낮을 때 바꿔 볼 값

**한 번에 하나만** 바꾸고, `train`의 **교차검증**으로 비교, **2~3번 안에서** 정할 것 (많이 바꿔 볼수록 그 데이터에 맞춰지는 과대적합). 시연용 기록으로는 비교하지 말 것.

| 증상 | 바꿔 볼 것 (위가 먼저) | 대가 |
|---|---|---|
| **오경보가 많음** | ① 정상 기록을 여러 조건으로 추가 (가장 효과 큼) | — |
| | ② 바닥이 바뀌는 곳이면 `segment` 기록, 또는 `CAL_SPLIT = "interleave"` | 고장 감지도 줄 수 있음 |
| | ③ `WHEEL_SCORE = False` | 한 바퀴 고장 감지가 줄어듦 |
| | ④ `check`에 튀는 값 경고가 많으면 `SPIKE_K = 8` | — (실제 충격은 안 뺌) |
| | ⑤ `CONFIRM_PERIODS = 3` | 경보가 1분 늦어짐 |
| **고장을 놓침** | ① diagnose 그래프에서 고장이 점수에 드러나는지, 엔코더 4개가 다 사는지 확인 | — |
| | ② `CAL_SPLIT = "tail"` (지금 값) 유지 | 오경보가 조금 늘 수 있음 |
| | ③ 간헐 고장이면 `PERIOD_QUANTILE = 0.75` | 오경보가 늘 수 있음 |
| | ④ `CONFIRM_PERIODS = 1` 또는 `PERIOD_S = 30` | 오경보가 늘어남 |
| **경고가 늦음** | `FAIL_CAL_BAND` 낮게(예: 0.65~0.75), `THRESH["warning"]` 6 → 5 | '정지 위험'의 뜻이 바뀜 |
| **원인을 틀림** | 고장 종류마다 기록 2개 이상, 엔코더 4개 확보 | — |
| **기록마다 결과가 들쭉날쭉** | `BASELINE_PERIODS` 5 → 7~10, `AE_ENSEMBLE = 3` | 기록이 길어야 함 / 학습이 느려짐 |

**바꾸지 말 것:** `SCORE_MAX`, `MIN_FAIL_RATIO`, 오토인코더 크기(24-6-24)·원인 분류 나무 설정 — 키우면 학습 데이터를 외우기 쉬워짐.
값을 바꾸면 **`train`부터 다시** (판정 주기·1분 점수 방식·연속 횟수는 모델 파일에 저장되어 진단에 그대로 쓰임).

## 6. 모델이 동작하는 방식 (자세히)

1. **읽기** (`dataio.py`): 단위를 맞추고(µs→초, 원래값→g·°/s, mA→A), 엔코더 값을 누적 펄스로 바꾸고, **엔코더 4개의 상태**(정상·죽음·도중에 멈춤)를 판정합니다. 죽은 엔코더는 없는 것으로 처리합니다. 1초씩 자릅니다.
2. **특징** (`features.py`): 1초마다
   - 진동 36개 = 6축 × (진동 크기 RMS, 첨도, 크레스트, 저·중·고주파 에너지)
   - 바퀴 11개 (엔코더 4개가 있을 때) = 바퀴 4개 × (상대 속도: 다른 세 바퀴보다 빠르거나 느린 비율, 속도 흔들림: 다른 바퀴와 다르게 출렁이는 정도) + 왼쪽·오른쪽 앞뒤 속도 차이 + 모터 명령 대비 속도. **바퀴가 실제로 도는 구간만**으로 계산
3. **정상 기준** (`models.SegmentBaseline`): 로봇마다 처음 5분의 평균·표준편차 → 이후 1초를 "평소보다 몇 배 벗어났나"(z)로 바꿈
4. **이상 점수**:
   - 오토인코더: 정상 z만으로 학습한 신경망(47→24→6→24→47)이 복원하지 못한 정도
   - 바퀴 이상 점수: 네 바퀴 중 **한 바퀴만 외톨이처럼** 벗어난 정도 (네 바퀴가 함께 흔들리는 바닥 영향은 작게 나옴)
   - 두 점수를 각각 "학습에 안 쓴 정상 로봇의 99.5% = 3점, 고장 정도 0.75~0.85 = 9점" 눈금에 맞춘 뒤 **큰 쪽**이 건강 점수
   - 비교용 모델 3개(z-score, ECOD, PCA)도 함께 학습해 교차검증 비교표·`fig_auc.png`에만 나옴 (판정에는 안 씀). Isolation Forest는 가상 시험에서 늘 가장 낮아 11/11에 뺐음 (그 전에 학습한 모델 파일은 다시 학습해야 열림)
5. **판정** (`infer.py`): 1분마다 1초 점수의 중앙값 → 3점 미만 정상, 6점 미만 주의, 그 이상 경고. **2번 연속**일 때만 상태 변경(9점 이상은 바로)
6. **원인**: 주의 이상일 때 랜덤포레스트가 고장 종류·바퀴 확률을 내고, SHAP으로 판단 근거 3개
7. **전류·배터리** (`power.py`): AI와 별도. 처음 5분 대비 전류가 높은 상태가 2분 연속이면 '전류 높음', 7.0 V 아래면 '배터리 낮음', 사용량 mAh

| 0 | 진동만 (특징 36개) | 82.2% | 가벼운 시험 |
| 1 | 엔코더 바퀴 특징 추가 | 73.3% ↓ | 멈추거나 출발할 때 0 근처 속도로 나눠 값이 튐 → 정상도 이상처럼 보임 |
| 2 | **바퀴가 도는 구간만** 계산 | 86.7% | 가벼운 시험 |
| 3 | (2번을 시험 ①에서 측정) | **80.0%** | 시험 ① 개선 전 |
| 4 | **바퀴 상대 속도** + **바퀴 이상 점수**(큰 쪽 사용) | 91.1% | 개발용 · 바닥 오경보 2/2 |
| 5 | 가장 튄 바퀴 − 네 바퀴 중앙값 | 93.3% | 개발용 · 바닥 오경보 1/2 |
| 6 | 네 바퀴 흩어짐으로 나눔 (외톨이 점수) | 93.3% | 개발용 · 최종 |
| 7 | 6번을 시험 ①에 **한 번만** | **91.1%** | 시험 ① 개선 후 (고장 감지 67.9% → 89.3%) |

효과가 없거나 나빴던 것: 학습 로봇 4배(+1%p), 1분 점수 상위 25% 지점(오경보 증가), 오토인코더 3개 평균·튀는 값 빼기·보정 로봇 고루 섞기(오경보는 0%가 됐지만 정답률 80%로 하락 → 끔).

**왜 올라갔나:** 데이터·모델을 키운 것이 아니라, **"바퀴 고장은 한 바퀴에만 생기고, 주행 상태·바닥은 네 바퀴 모두에 영향을 준다"**는 차이를 점수로 만든 것이 핵심입니다.
- 바퀴 속도 자체는 주행·정지·회전에 따라 크게 변함 → **상대 속도**로 주행 영향을 지움
- 오토인코더는 47개 특징을 평균 내서 바퀴 하나의 이상이 묻힘 → **바퀴 이상 점수**를 따로 봄
- 바닥이 거칠면 네 바퀴가 함께 흔들림 → **외톨이 점수**로 공통 흔들림을 지움

**과대적합 방지:** 개발용 가상 로봇(seed 3001)으로만 고르고, 처음 보는 시험 로봇에는 한 번만 돌렸습니다. 개발용 93.3% ↔ 시험 91.1%로 비슷합니다.

### 7-3. 왜 가상에서는 성능이 좋게 나왔나 (실측은 더 낮을 가능성이 큼)

| 가상 데이터 | 실측에서 |
|---|---|
| 고장이 바퀴 속도·진동에 주는 영향을 **사람이 식으로 정함** (베어링 15% 느려짐 등) | 실제 고장이 엔코더에 그만큼 드러나는지 모름 |
| 정상 로봇이 얌전함 (잡음이 일정) | 바닥·배터리·온도·미끄러짐으로 정상 점수가 더 흔들림 → 오경보 또는 놓침 증가 |
| 로봇 수십 대 | 차체 1대 (교차검증이 좋게 나와도 다른 로봇에 통한다는 증거는 아님) |
| 고장 정도 라벨이 정확 | 사람이 정하는 값이라 흔들림 → 9점 눈금 부정확 |
| 엔코더 깨끗 | 해상도·빠진 펄스·미끄러짐 |

그래도 "고장 난 바퀴는 다른 바퀴와 다르게 돈다"는 원리는 실제 물리 현상이라 **엔코더를 쓰는 방향은 실측에서도 도움이 될 가능성이 높습니다.** 얼마나인지는 실측 교차검증으로만 알 수 있습니다.

## 8. 주의할 점

- **결과를 보고 설정을 여러 번 바꾸지 말 것** (과대적합). 시연용 기록은 마지막에 한 번만
- 발표에는 **실측 교차검증 수치만**. 가상 수치는 코드 점검용
- 엔코더로 학습한 모델은 진단할 기록에도 엔코더 4개가 있어야 함 (없으면 알려 줌)
- `check`의 **엔코더 상태**: '죽음'이면 그 엔코더를 빼고(4개 미만이면 진동만으로 진단), '도중에 멈춤'이면 선 빠짐 의심 → 바퀴 고장이 아니라 센서 이상일 수 있음
- 배터리 A/B를 정상·고장 기록에 골고루. 같은 로봇 이름으로 배터리를 바꿔 이어 기록하면 mAh가 이어서 더해짐
- 가상 시험(코드 점검, 성능 아님, 결과는 `가상테스트_결과/README.md`):
  - 빠른 확인 약 4분: `python 가상테스트/test_complex.py --scale 0.1 --encoders`
  - 학습 약 10분 + 시험 약 10분: `python 가상테스트/test_complex.py --train-scale 0.8 --test-scale 0.75 --encoders` (가상 기록 만들기 약 7분 별도. VS Code 목록에도 있음. 이 컴퓨터 실측: 0.45·0.5일 때 학습 5.6분·시험 6.5분)
  - `--train-scale`·`--test-scale`로 학습·시험 로봇 수를 따로 정함 (시험 로봇은 학습과 다른 seed로 만들어 겹치지 않음)
- 외부 데이터 시험(동작 확인, 우리 로봇 성능 아님): 회전기계 테스트베드(6 kHz, 센서 2개, 정상·축 불평형·기어 이 빠짐)를 로봇 13대 CSV로 늘려 맞춘 것
  - 만들기: `python 외부데이터_시험/만들기.py` (원본 폴더가 다르면 `--src 폴더`) → `외부데이터_시험/data/*.csv.gz`
  - 실행: VS Code 목록 **외부 데이터 시험 1 → 2 → 3** (= `python run.py check|train|diagnose --path 외부데이터_시험/data`)
  - 결과는 실측과 같은 `reports/`·`artifacts/`에 덮어씀 → 실측 CSV로 다시 `train`하면 실측 결과로 바뀜
  - 맞춘 방법(정상 6분 + 고장 단계별 이어 붙이기, 로봇마다 빠르기 0.97~1.03배·크기 0.9~1.1배, 센서 2개로 6축 채우기, 6 kHz → 1 kHz)과 한계(정상 기록 10개를 여러 로봇이 다시 씀)는 `만들기.py` 맨 위 설명
  - 처음 정상 주행 시간 비교: `만들기.py --normal-first 4 --out 외부데이터_시험/data_정상4분` (3분도 같은 방식) → `python 외부데이터_시험/기준시간_비교.py` (약 15분, 결과 `가상테스트_결과/기준시간_비교.md`)
    - 11/11 결과: 정상 6분(기준 5분)·4분(기준 3분)·3분(기준 2분) 모두 로봇 단위 결과가 같음 (정답률 76.9%, 감지 6/9, 오경보 0/4). 정상 3분인데 기준 5분을 그대로 두면 공통 기준(reference)으로 바뀌고 원인 분류가 91.8% → 84.0%로 떨어짐
    - 단, 이 데이터는 일정한 속도로 도는 기계라 정상 상태가 2분 안에 다 나옴. 주행·정지·회전이 섞이는 로봇은 다를 수 있으니, 실측은 6분 이상 기록해 두고 `BASELINE_PERIODS`만 바꿔 같은 기록으로 비교할 것
