# AMR 고장예지 AI — 실측 데이터 전용

모든 모델은 `data/`에 넣은 실측 CSV로만 학습·평가합니다. 학습·진단 코드(`run.py`, `pipeline/`)는 가상 데이터를 만들거나 섞지 않습니다.

> 예외 하나: `가상테스트/`는 **코드 점검 전용** 도구입니다. 무작위 가상 로봇(기본 100대)을 메모리에서만 만들어 학습·진단·채점 코드가 끝까지 도는지 보고,
> 결과를 `가상데이터_결과값/로봇100대/`에 %로 남깁니다. `test_complex.py`는 복잡한 고장(급성·간헐·복합 등)까지 학습시키고
> 어려운 로봇까지 넣어 시험합니다 (`가상데이터_결과값/복잡한고장_학습시험/`). `data/`에는 아무것도 쓰지 않으며, 그 %는 성능이 아닙니다.

지금까지의 구성과 실험 전체 요약은 [진행_요약.md](진행_요약.md)에 있습니다.
설정을 바꾸고 싶으면 [파라미터_설명.md](파라미터_설명.md)에서 바꿀 수 있는 값과 주의할 점을 먼저 보세요.

**센서 구성 (4WD 시험 로봇):**
- MPU6050 1개: 차체에 고정. 가속도 3축 + 각속도 3축 → **진동 AI** (학습 필요)
- INA219 1개: 배터리와 모터 드라이버 사이. 로봇 전체 전류 + 배터리 전압 → **전류·배터리 감시** (학습 없이 동작)
- 배터리 잔량 센서는 없습니다. 배터리는 INA219의 전압과, 전류를 시간에 따라 더한 사용량[mAh]으로 봅니다.
- 속도(인코더)·온도는 쓰지 않습니다. 없는 값을 기본값이나 다른 값으로 채워 넣지 않아서, 필요한 열이 없으면 추측하지 않고 오류로 알려 줍니다.

## 실행

| 순서 | 실행 파일 (`실행/`) | 명령 | 결과 |
|---|---|---|---|
| 1 | `1_환경설치.py` | | `.venv` 생성, 패키지 설치 (처음 한 번) |
| 0 | `0_아두이노_기록.py` | | 아두이노 USB 시리얼 → `data/<로봇>_<날짜_시각>.csv` (기록할 때마다) |
| 2 | `2_데이터_검사.py` | `python run.py check` | 형식 검사, 정상 기준 방식 결정 |
| 3 | `3_학습_평가.py` | `python run.py train` | 로봇 단위 교차검증 → `reports/`, 최종 모델 → `artifacts/` |
| 4 | `4_진단.py` | `python run.py diagnose` | 로봇별 진단 (분 단위) → `reports/diagnose/` |

아두이노 연결과 스케치 올리기는 [`arduino/README.md`](arduino/README.md)를 보세요.

VS Code는 이 폴더를 열고 왼쪽 "실행 및 디버그"에서 고르면 됩니다. Visual Studio는 폴더 열기 → 실행 파일 오른쪽 클릭 → 시작 항목으로 설정 → Ctrl+F5.

공통 옵션: `--path 경로`(기본 `data`), `--fs 500`(time 열이 없을 때 센서의 실제 샘플링 Hz), `--period-s 60`(판정 주기 초), `--baseline auto|per_unit|reference`, `train --no-eval`(교차검증 없이 최종 모델만).

## 구성

```
아두이노 (MPU6050 + INA219) → USB 시리얼 → 0_아두이노_기록.py → data/*.csv
  │
  ├─ 진동 AI (학습한 모델)
  │    MPU6050 6축 → 1초 창 → 특징 36개 → [구간별 정상 기준] z-score
  │         ├→ [오토인코더] 건강 점수 0~ (3 주의 · 6 경고 · 9 정지 위험)
  │         │      → 판정 주기(기본 1분) 중앙값(기본) → 상태 (기본 2번 연속일 때만 변경)
  │         │      → [칼만 필터] 정지 위험까지 남은 시간(분) + 90% 범위
  │         └→ [랜덤포레스트] 고장 종류(+라벨에 적은 바퀴) 확률 → [SHAP] 판단 근거 상위 3개
  │
  └─ 전류·배터리 감시 (학습 없음, 로봇마다 처음 5분 = 평소)
       INA219 전류 → 평소의 99.5% 지점을 넘는 상태가 2분 연속이면 '전류 높음' + 평소 대비 몇 배
       INA219 전압 → 배터리 전압, 7.0 V 아래면 '배터리 낮음'
       전류 × 시간 → 기록 시작 이후 사용량 [mAh], 용량(1500 mAh) 대비 %
```

### 진동 AI

| 역할 | 모델 | 설정 | 학습 데이터 |
|---|---|---|---|
| 정상 기준 | 구간별 평균·표준편차 | 표준편차 하한 = 0.001 + 평균의 5% | 로봇의 처음 5분 또는 정상 로봇 공통 |
| **이상 감지 (주 모델)** | **오토인코더** (MLP 36-24-6-24-36, tanh) | 조기 종료, 정상만 학습 | 정상 창 |
| 이상 감지 비교 | z-score 평균, ECOD, Isolation Forest, PCA(6성분) | ECOD·Isolation Forest는 PyOD가 기본으로 권하는 기준선 | 정상 창 |
| 건강 점수 눈금 | 분위수 보정 | 정상 99.5% = 3, 고장 기준 창 중앙값 = 9 (로그 눈금) | 학습에 안 쓴 정상 로봇 + 고장 창 |
| 원인 분류 | 랜덤포레스트 | 150그루, 잎 최소 3, 클래스 균형 | 고장 라벨 창 (정도 0.25 이상) + 정상 |
| 판단 근거 | SHAP TreeExplainer | 판정 클래스 기여도 상위 3개 | — |
| 남은 시간 | 칼만 필터 (수준·기울기 2상태) | 잡음 값을 학습 고장 기록으로 격자 탐색 | 9점까지 간 학습 고장 로봇 |
| 비교 | 추세선 (최근 6주기 직선) | — | — |

**특징 36개** = 축 6개(ax, ay, az, gx, gy, gz) × 6개

| 종류 | 축마다 | 잡는 고장 신호 |
|---|---|---|
| RMS (진동 크기) | 1 | 전반적으로 흔들림이 커짐 — 불평형, 풀림 |
| 첨도, 크레스트 | 2 | 뾰족한 충격이 섞임 — 베어링·기어 표면 손상의 초기 신호 |
| 저(1~20 Hz)·중(20~150 Hz)·고(150 Hz 이상) 주파수 에너지 | 3 | 어느 대역이 커졌는가 — 고장 종류마다 다름 |

- 센서가 하나라서 **진동만으로는 어느 바퀴인지 구분하기 어렵습니다.** 고장 실험 때 `fault_wheel`(어느 바퀴에 고장을 냈는지)을 라벨로 적으면 원인 분류가 "종류 + 바퀴"로 배우지만, 바퀴마다 진동 패턴이 충분히 다를 때만 맞힙니다.
- 속도 데이터가 없으므로 회전 주파수(1X) 특징은 계산하지 않습니다(속도를 가정하면 임의 값이 되기 때문).

### 전류·배터리 감시 (`pipeline/power.py`)

전류·전압은 학습 데이터에 없어도 됩니다. 진단할 때 **로봇마다 처음 5분을 그 로봇의 평소로 삼아** 비교합니다(진동의 per_unit 기준과 같은 생각).

| 결과 칸 | 계산 |
|---|---|
| `전류(A)` | 그 주기(1분)의 평균 전류 |
| `전류 평소 대비(배)` | 그 주기 평균 ÷ 처음 5분 평균. 1.3이면 30% 더 먹음 = 배터리가 그만큼 빨리 닳음 |
| `전류 상태` | 처음 5분 동안 1초 평균 전류의 99.5% 지점을 그 주기 창의 절반 넘게 넘으면 '높음' 쪽. 2주기 연속일 때만 바뀜 → 마찰·걸림·베어링 손상·과적처럼 모터가 힘들게 도는 상태 |
| `사용량(mAh)`, `용량 대비 사용(%)` | 전류를 시간에 따라 더한 값. 기록 시작 이후 쓴 양 (시작할 때 얼마나 충전돼 있었는지는 모르므로 '남은 양'이 아님) |
| `배터리 전압(V)`, `배터리 상태` | 그 주기 전압의 중앙값. 7.0 V(셀당 3.5 V) 아래면 '낮음'. 모터가 돌 때 잠깐 떨어지는 전압은 중앙값으로 걸러짐 |

기준값(`BATTERY_CAPACITY_MAH`, `BATTERY_LOW_V`, `POWER_QUANTILE`)은 `config.py`에서 바꿉니다. current·voltage 열이 없는 기록은 이 칸 없이 진동만으로 진단합니다.

### 판정 주기 (회차 대신)

정해진 경로를 반복하지 않는 운행이라 '회차'를 쓰지 않습니다. 1초 창의 건강 점수를 **판정 주기**(`config.PERIOD_S`, 기본 60초)마다 묶어 중앙값으로 상태를 정하고, 2번 연속(기본 2분)일 때만 상태를 바꿉니다. 중앙값 대신 높은 쪽 값을 쓰거나(`config.PERIOD_QUANTILE`) 연속 횟수를 바꿀 수 있습니다(`config.CONFIRM_PERIODS`, [파라미터_설명.md](파라미터_설명.md)). 정상 기준(per_unit)은 처음 5주기(5분), 남은 시간과 여유 시간은 모두 분으로 표시합니다. `python run.py train --period-s 30`처럼 바꿀 수 있고, 학습 때 정한 값은 모델에 저장되어 진단할 때 그대로 쓰입니다. 기록이 끊긴 시간(로봇이 꺼져 있던 시간)은 건너뛰고 기록된 시간 기준으로 셉니다.

## 데이터 형식

`0_아두이노_기록.py`가 만드는 CSV가 그대로 이 형식입니다. 다른 방법으로 기록했다면 열 이름만 맞추면 됩니다.

CSV 한 줄 = 샘플 하나, 파일 하나 = 로봇 1대(같은 `robot` 값의 파일 여러 개는 이어 붙임).

```csv
time,ax,ay,az,gx,gy,gz,current,voltage,robot
0.000,0.01221,-0.00610,1.00098,0.4580,-0.1527,0.0763,0.31250,8.104,R1
0.002,0.00977,-0.00488,0.99854,0.3053,-0.1527,0.0000,,,R1
```

**필수 열**

| 열 | 설명 | 없을 때 |
|---|---|---|
| `ax`, `ay`, `az` | MPU6050 가속도 [g]. `acc_x`, `accel_x`처럼 이름이 조금 달라도 알아들음(`config.CHANNEL_ALIASES`) | **오류.** 한 축이라도 없으면 채우지 않고 멈춤 |
| `gx`, `gy`, `gz` | MPU6050 각속도 [°/s]. `gyro_x` 등 | **오류** |
| `time` | 시각 [초] 또는 날짜·시각. 샘플링 주파수를 여기서 계산 | `--fs`로 실제 샘플링을 알려 주면 그걸로 시각 계산, 둘 다 없으면 **오류** |

진동 샘플링은 100 Hz 이상이어야 하고, 300 Hz보다 낮으면 고주파(150 Hz 이상) 특징이 거의 비게 된다고 경고합니다. 아두이노 스케치는 500 Hz로 기록합니다.

**다른 기록 스케치의 형식도 자동으로 맞춰 읽습니다.** 바꾼 내용은 모두 `check`의 "확인할 점"에 나옵니다.

| 이런 열이 있으면 | 이렇게 읽음 |
|---|---|
| `t_us`·`micros`, `t_ms`·`millis` | 초로 바꿈. micros()가 2^32에서 0으로 돌아가도 이어 붙임 |
| `time`이 밀리초나 마이크로초 | 샘플링이 100 Hz보다 낮게 계산되면 단위를 알아채 초로 바꿈 |
| 가속도·각속도가 센서 원래 정수값 (가속도 값이 50 넘음) | 가속도 ÷`RAW_ACCEL_LSB_PER_G`(8192 = ±4g), 각속도 ÷`RAW_GYRO_LSB_PER_DPS`(65.5 = ±500°/s). **스케치의 센서 범위 설정과 같아야 함** |
| `mV`, `mA` | V, A로 바꿈 |
| 전류·전압이 모두 0 | INA219를 못 읽은 것으로 보고 쓰지 않음 |
| 열 이름 끝의 단위 `시간(ms)`, `전류(mA)`, `전압 [mV]`, `gx(raw)` | 단위를 떼고 표준 단위로 바꿈 |
| `current`·`voltage`인데 값이 mA·mV 크기 (전류 20 넘음, 전압 100 넘음) | 1000으로 나눔 |
| `label` | 고장 종류로 읽음. `idle`, `stop`, `normal`은 정상 |
| 엔코더 4개 `enc1`~`enc4`, `enc_fl`… , `엔코더1`… | 누적 펄스 → 1초마다 **바퀴 속도[펄스/초]**. 1 = 앞 왼쪽, 2 = 앞 오른쪽, 3 = 뒤 왼쪽, 4 = 뒤 오른쪽. 아두이노 `int`(16비트) 넘침도 이어 붙임 |
| 모터 명령 `cmd`, `pwm`, `spd`, `motor`, `모터명령`… | 1초 평균 |
| 그 밖의 열 | "쓰지 않은 열"로 알림 |

엔코더와 모터 명령은 **아직 AI 입력에는 넣지 않고** `check` 표(엔코더 몇 개, 모터 명령 있음)와 `diagnose` 표(1분마다 바퀴 속도, 모터 명령)에만 보여 줍니다. 실측 데이터로 효과를 확인한 뒤 특징으로 넣을지 정합니다.

예) `시간, ax, ay, az, gx, gy, gz, 엔코더 4개, 모터 명령, 전류, 전압` 형식이 그대로 읽힙니다.
`t_us,ax,ay,az,gx,gy,gz,enc1,enc2,enc3,enc4,cmd,mA,mV,label`이나 `시간(ms),…,엔코더1,…,모터명령,전류(mA),전압(mV)`도 마찬가지입니다.
`robot` 열이 없으면 **파일 이름이 로봇 이름**이 되므로, 같은 기록을 나눠 저장했다면 파일 이름 대신 `robot` 열을 넣어 주세요.

**선택 열** (없어도 됨, 값을 만들어 넣지 않음)

| 열 | 설명 | 없을 때 |
|---|---|---|
| `current` | INA219 전류 [A]. 몇 줄에 한 번만 값이 있어도 됨 | 전류 감시·사용량 계산 안 함 |
| `voltage` | INA219 전압 = 배터리 전압 [V] | 배터리 전압 감시 안 함 |
| `robot` | 로봇 이름 | 파일 이름 |
| `segment` | 구간(장소, 노면) | 전체를 한 구간으로 보고 기준을 만듦 |
| `bump` | 문턱 통과 0/1 | 문턱 순간을 판정에서 빼지 못함 |
| `fault_kind`, `fault_wheel`, `fault_severity` | 라벨 (학습·평가용). 예: `looseness`, `fr`, `0.5` | 라벨 없는 로봇은 정상으로 보고 학습·평가. 고장 라벨이 하나도 없으면 원인 분류·남은 시간 예측을 하지 않음 |

열 이름이 다르면 `config.py`의 `COLUMN_ALIASES`에 추가하세요.

### 정상 기준 방식 (`--baseline`, 진동 AI)

- **per_unit**: 로봇마다 처음 5분(5주기)으로 그 로봇만의 구간별 기준을 만듭니다. 운행을 정상 상태에서 시작하는 기록에 맞습니다. **그래서 기록은 6분 이상 하세요.**
- **reference**: 학습용 정상 로봇들을 모아 공통 기준을 만듭니다. 처음부터 고장인 기록에 필요합니다.
- **auto** (기본): 처음 5분에 고장 라벨이 있거나 기록이 그보다 짧은 로봇이 있으면 reference.

reference 방식은 정상 기록이 적으면 처음 보는 정상 기록을 이상으로 봅니다. 정상 기록(서로 다른 날·배터리·조립 상태)은 3개 이상, 가능하면 5개 이상 넣으세요.

## 설계 근거 (참고한 신뢰할 수 있는 자료)

1. **평가는 로봇 단위로 나눈다.** 같은 장비의 창이 학습과 평가에 섞이면 장비 고유 특성을 외워 성능이 부풀려집니다. 장비 단위 분할의 중요성을 다룬 연구: Vieira et al., *Towards a more realistic evaluation of machine learning models for bearing fault diagnosis*, [arXiv:2509.22267](https://arxiv.org/abs/2509.22267v1) (2025). → `workflow.cross_validate`는 평가 로봇을 정상 기준·눈금 보정·학습 어디에도 쓰지 않습니다.
2. **비교 기준선은 검증된 기본값을 쓴다.** 이상 감지 라이브러리 [PyOD](https://pypi.org/project/pyod/)와 벤치마크 ADBench 저자들은 잘 모를 때 Isolation Forest와 ECOD를 기본으로 권합니다. → 오토인코더가 이 둘보다 나은지 같은 조건에서 비교합니다. ECOD는 의존성을 늘리지 않으려고 논문(Li et al., TKDE 2022) 정의대로 직접 구현했습니다.
3. **건강 지표의 품질을 잰다.** 예지 정비에서 건강 지표는 단조성·추세 일치도·고장 시점 일관성으로 평가합니다 ([MathWorks Predictive Maintenance Toolbox](https://ch.mathworks.com/help/predmaint/ug/feature-selection-for-remaining-useful-life-prediction.html)). → 진행형 고장 기록이 있으면 `health_indicator` 항목에 계산됩니다. 기록이 적으면 이 값은 믿기 어렵습니다.
4. **남은 수명 예측은 상태 추정 문제로 푼다.** NASA의 예지 정비 라이브러리 [ProgPy](https://github.com/nasa/progpy)도 상태 추정 + 예측 구조입니다. 여기서는 데이터가 적은 상황에 맞춰 2상태 칼만 필터만 쓰고, 잡음 값은 학습 데이터로 맞춥니다.

## 결과를 볼 때 주의

- `reports/`의 수치는 **로봇 단위 교차검증** 결과입니다. 학습에 쓴 기록을 `diagnose`로 진단한 결과는 성능이 아닙니다.
- 기록이 적으면 수치가 크게 흔들립니다. 몇 개로 평가했는지 함께 발표하세요.
- 고장 정도(`fault_severity`) 라벨이 없으면 9점 눈금은 고장 창 전체의 중앙값으로 맞추고, 정지 위험 전 경고 여유는 계산하지 않습니다.
- 속도 데이터가 없으므로 속도가 크게 바뀌는 운행에서는 속도 변화가 진동·전류 이상으로 보일 수 있습니다. 처음 5분(평소)에 실제 운행과 비슷한 속도·정지가 섞여 있어야 오경보가 줄어듭니다.
- 전류 감시는 학습하지 않은 규칙이라 성능 수치(AUC 등)가 없습니다. 발표할 때는 "처음 5분 대비 비교 규칙"이라고 설명하세요.
