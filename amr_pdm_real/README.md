# AMR 고장예지 AI — 실측 데이터 전용

가상(시뮬레이션) 데이터를 전혀 쓰지 않는 버전입니다. 시뮬레이터 코드가 없고, 모든 모델은 `data/`에 넣은 실측 CSV로만 학습·평가합니다. 시뮬레이션 버전은 옆 폴더 `amr_pdm/`에 그대로 있습니다.

## 실행

| 순서 | 실행 파일 (`실행/`) | 명령 | 결과 |
|---|---|---|---|
| 1 | `1_환경설치.py` | | `.venv` 생성, 패키지 설치 |
| (선택) | `공개데이터_Paderborn.py` | `python run.py paderborn download --bearings ...` 후 `convert` | 공개 실측 데이터 → `data/` |
| 2 | `2_데이터_검사.py` | `python run.py check` | 형식 검사, 정상 기준 방식 결정 |
| 3 | `3_학습_평가.py` | `python run.py train` | 로봇 단위 교차검증 → `reports/`, 최종 모델 → `artifacts/` |
| 4 | `4_진단.py` | `python run.py diagnose` | 로봇별 진단 (분 단위) → `reports/diagnose/` |

VS Code는 이 폴더를 열고 왼쪽 "실행 및 디버그"에서 고르면 됩니다. Visual Studio는 폴더 열기 → 실행 파일 오른쪽 클릭 → 시작 항목으로 설정 → Ctrl+F5.

## AI 모델 구성

```
CSV (진동·전류·배터리 잔량·속도)      ※ 온도는 쓰지 않음
  → 1초 창 → 특징 70개 (4륜 기준. 배터리: 최근 3칸(3%)이 떨어지는 데 걸린 시간 = 소모 속도 %/분)
  → [Ridge 회귀] 정상 전류 예측 → 전류 잔차
  → [Ridge 회귀] 정상 배터리 소모 예측 → 초과 소모
  → [구간별 정상 기준] z-score  (로봇마다 / 정상 로봇 공통)
       ├→ [오토인코더] 건강 점수 0~ (3 주의 · 6 경고 · 9 정지 위험)
       │      → 판정 주기(기본 1분) 중앙값 → 상태 (2번 연속일 때만 변경)
       │      → [칼만 필터] 정지 위험까지 남은 시간(분) + 90% 범위
       └→ [랜덤포레스트] 고장 종류(+바퀴) 확률 → [SHAP] 판단 근거 상위 3개
  → [배터리 소모 비율] 잔량이 한 칸 떨어질 때마다: 최근 3칸의 실제 소모 / 같은 시간의 예상 소모
         학습한 정상 기준(정상 측정의 99.5% 지점)을 2번 연속 넘으면 '배터리 소모 이상'
```

### 배터리 소모 이상을 잡는 방법

"학습한 정상보다 배터리가 빨리 닳는가"를 두 갈래로 봅니다.

1. **직접 비교 (설명하기 쉬움):** 정상 로봇 기록으로 "이 속도·가속도·구간이면 분당 몇 % 닳는다"를 배웁니다(Ridge 회귀). 잔량이 한 칸 떨어질 때마다 "최근 3%가 떨어지는 동안 정상이라면 몇 %를 썼어야 하나"를 계산해 **배수**를 내고, 학습에 쓰지 않은 정상 로봇 측정값의 99.5% 지점을 넘는 일이 2번 연속이면 경고합니다. 결과 표의 `배터리 소모(예상 대비 배)` 열이 1.0이면 정상과 같고, 1.3이면 30% 빨리 닳은 것입니다.
2. **다른 신호와 함께 (AI):** 소모 속도와 초과 소모를 특징으로 넣어 오토인코더 건강 점수와 원인 분류에도 반영합니다. 진동이나 전류 이상과 배터리 소모가 같이 늘면 더 확실하게 잡힙니다. 라벨을 `fault_kind=battery`로 달면 원인 분류가 "배터리 이상 소모"를 따로 배웁니다.

- 잔량은 1% 단위로 천천히 바뀌어 짧은 시간 구간의 기울기는 0 아니면 1%라 크게 흔들립니다. 그래서 시간이 아니라 **잔량 칸이 바뀐 시각**을 기준으로 잽니다(`config.BATTERY_STEP`, `BATTERY_DROPS`). 처음 5분 기울기 방식으로 시험했을 때는 경고 기준이 예상의 1.98배까지 올라가 1.6배 빨리 닳는 로봇을 놓쳤습니다.
- 처음 4칸이 떨어지기 전에는 비율을 잴 수 없습니다. 소모가 0.3 %/분이면 약 13분이 걸립니다.
- 잔량이 오르면(충전) 기록을 다시 시작하고, 다음 칸이 떨어질 때까지는 판정에서 뺍니다.
- 소모 속도는 적재 무게에도 달려 있습니다. 적재량이 크게 바뀌는 운행이라면 정상 기록에 그런 운행이 충분히 들어 있어야 오경보가 줄어듭니다.

| 역할 | 모델 | 설정 | 학습 데이터 |
|---|---|---|---|
| 정상 전류 예측 | Ridge 회귀 | alpha 0.001, 입력: 구간·속도·가속도 | 정상 창 |
| 정상 배터리 소모 예측 | Ridge 회귀 | 위와 같은 입력, 출력: 소모 %/분 | 정상 창 |
| 배터리 소모 경고 | 실제/예상 소모 배수 | 기준 = 정상 로봇을 한 대씩 빼고 잰 비율의 99.5% 지점(최소 1.15배), 2번 연속 | 정상 로봇 |
| 정상 기준 | 구간별 평균·표준편차 | 표준편차 하한 = 센서 분해능 + 평균의 5% | 로봇의 처음 5분 또는 정상 로봇 공통 |
| **이상 감지 (주 모델)** | **오토인코더** (MLP 70-24-6-24-70, tanh, 4륜 기준) | 조기 종료, 정상만 학습 | 정상 창 |
| 이상 감지 비교 | z-score 평균, ECOD, Isolation Forest, PCA(6성분) | ECOD·Isolation Forest는 PyOD가 기본으로 권하는 기준선 | 정상 창 |
| 건강 점수 눈금 | 분위수 보정 | 정상 99.5% = 3, 고장 기준 창 중앙값 = 9 (로그 눈금) | 학습에 안 쓴 정상 로봇 + 고장 창 |
| 원인 분류 | 랜덤포레스트 | 150그루, 잎 최소 3, 클래스 균형 | 고장 라벨 창 (정도 0.25 이상) + 정상 |
| 판단 근거 | SHAP TreeExplainer | 판정 클래스 기여도 상위 3개 | — |
| 남은 시간 | 칼만 필터 (수준·기울기 2상태) | 잡음 값을 학습 고장 기록으로 격자 탐색 | 9점까지 간 학습 고장 로봇 |
| 비교 | 추세선 (최근 6주기 직선) | — | — |

### 판정 주기 (회차 대신)

정해진 경로를 반복하지 않는 운행이라 '회차'를 쓰지 않습니다. 1초 창의 건강 점수를 **판정 주기**(`config.PERIOD_S`, 기본 60초)마다 묶어 중앙값으로 상태를 정하고, 2번 연속(기본 2분)일 때만 상태를 바꿉니다. 정상 기준(per_unit)은 처음 5주기(5분), 남은 시간과 여유 시간은 모두 분으로 표시합니다. `python run.py train --period-s 30`처럼 바꿀 수 있고, 학습 때 정한 값은 모델에 저장되어 진단할 때 그대로 쓰입니다. 기록이 끊긴 시간(로봇이 꺼져 있던 시간)은 건너뛰고 기록된 시간 기준으로 셉니다.

## 설계 근거 (참고한 신뢰할 수 있는 자료)

1. **평가는 로봇(베어링) 단위로 나눈다.** 같은 장비의 창이 학습과 평가에 섞이면 장비 고유 특성을 외워 성능이 부풀려집니다. 베어링 단위 분할과 학습 베어링 수의 중요성을 다룬 연구: Vieira et al., *Towards a more realistic evaluation of machine learning models for bearing fault diagnosis*, [arXiv:2509.22267](https://arxiv.org/abs/2509.22267v1) (2025). → `workflow.cross_validate`는 평가 로봇을 정상 기준·눈금 보정·학습 어디에도 쓰지 않습니다.
2. **비교 기준선은 검증된 기본값을 쓴다.** 이상 감지 라이브러리 [PyOD](https://pypi.org/project/pyod/)와 벤치마크 ADBench 저자들은 잘 모를 때 Isolation Forest와 ECOD를 기본으로 권합니다. → 오토인코더가 이 둘보다 나은지 같은 조건에서 비교합니다. ECOD는 의존성을 늘리지 않으려고 논문(Li et al., TKDE 2022) 정의대로 직접 구현했습니다.
3. **건강 지표의 품질을 잰다.** 예지 정비에서 건강 지표는 단조성·추세 일치도·고장 시점 일관성으로 평가합니다 ([MathWorks Predictive Maintenance Toolbox](https://ch.mathworks.com/help/predmaint/ug/feature-selection-for-remaining-useful-life-prediction.html)). → 진행형 고장 기록이 있으면 `health_indicator` 항목에 계산됩니다. 기록이 적으면 이 값은 믿기 어렵습니다.
4. **남은 수명 예측은 상태 추정 문제로 푼다.** NASA의 예지 정비 라이브러리 [ProgPy](https://github.com/nasa/progpy)도 상태 추정 + 예측 구조입니다. 여기서는 데이터가 적은 상황에 맞춰 2상태 칼만 필터만 쓰고, 잡음 값은 학습 데이터로 맞춥니다.
5. **공개 실측 데이터는 Paderborn 대학 베어링 데이터.** 정상 6개, 인공 손상 12개, 가속 수명 시험으로 생긴 실제 손상 14개 베어링, 진동·모터 전류·회전수를 기록(온도도 있지만 이 프로젝트에서는 쓰지 않고, 배터리 정보는 없음). 라이선스 CC BY-NC 4.0, 출처 표기 필수: Lessmeier et al., PHM Society European Conference 2016. 로더 구조는 공개 패키지 [paderborn-bearing](https://pypi.org/project/paderborn-bearing/)과 [dpmhm 데이터셋 문서](https://yanncalec.github.io/dpmhm/datasets/paderborn)를 참고했고, `.mat` 안의 신호는 위치가 아니라 이름(`vibration_1` 등)으로 찾습니다.

## 데이터 형식

CSV 한 줄 = 진동 샘플 하나, 파일 하나 = 로봇 1대. 필수 열은 `time`(초)과 바퀴 진동 열 하나 이상(g).

**바퀴 4개 전용**입니다(`config.WHEELS = ["fl", "fr", "rl", "rr"]` = 앞 왼쪽, 앞 오른쪽, 뒤 왼쪽, 뒤 오른쪽). 바퀴마다 `<바퀴>_vib`, `<바퀴>_cur` 열을 씁니다.

```csv
time,segment,speed,battery,fl_vib,fr_vib,rl_vib,rr_vib,fl_cur,fr_cur,rl_cur,rr_cur
0.000,복도A,1.02,87,0.0132,-0.0071,0.0040,0.0025,0.84,0.81,0.79,0.83
0.001,복도A,1.02,,0.0094,0.0023,-0.0012,0.0031,,,,
```

- `vib_fl`, `front_left_vib`처럼 이름이 조금 달라도 알아듣습니다(`config.WHEEL_ALIASES`).
- 센서가 없는 바퀴(예: 모터 없는 캐스터 바퀴)는 다른 바퀴 값으로 채우고, 그 바퀴의 고장 위치는 구분하지 않습니다.
- 바퀴 사이 비교 특징(`dev_`)은 "이 바퀴 − 나머지 세 바퀴 평균"입니다. 노면 영향은 모든 바퀴에 같이 와서 빠지고, 한 바퀴에만 생긴 고장이 남아 고장 바퀴 위치를 짚습니다.

| 열 | 설명 | 없을 때 |
|---|---|---|
| `battery` | 배터리 잔량 [%] (별칭: `soc`, `배터리`, `잔량`). 몇 초에 한 번만 값이 있어도 됨 | 배터리 소모 이상 판단 안 함 |
| `fl_cur` … `rr_cur` | 바퀴별 모터 전류 [A]. 교류 원신호면 창마다 RMS로 바꿈 | 일부만 있으면 있는 값으로 채움, 모두 없으면 전류 특징 0 |
| `speed` | 속도 [m/s] | 1 m/s 가정 |
| `segment` | 구간(노면, 운전 조건) | 전체를 한 구간 |
| `bump` | 문턱 통과 0/1 | 판정에서 빼지 못함 |
| `robot` | 로봇 이름 | 파일 이름 |
| `fault_kind`, `fault_wheel`, `fault_severity` | 라벨 (학습·평가용). `fault_wheel`은 `fl`·`앞 오른쪽`·`front-left` 등 | 모두 정상으로 보고 학습, 성능 평가 불가 |

열 이름이 다르면 `config.py`의 `COLUMN_ALIASES`에 추가하세요. 바퀴 반지름은 `WHEEL_RADIUS`.

### 정상 기준 방식 (`--baseline`)

- **per_unit**: 로봇마다 처음 5분(5주기)으로 그 로봇만의 구간별 기준을 만듭니다. 운행을 정상 상태에서 시작하는 실제 로봇 기록에 맞습니다.
- **reference**: 학습용 정상 로봇들을 모아 공통 기준을 만듭니다. 처음부터 손상된 베어링을 측정한 Paderborn 같은 데이터에 필요합니다.
- **auto** (기본): 처음 5분에 고장 라벨이 있거나 기록이 그보다 짧은 로봇이 있으면 reference.

reference 방식은 정상 로봇이 적으면 처음 보는 정상 로봇을 이상으로 봅니다. 시험해 보니 정상 로봇 2대로 교차검증하면, 한 대를 평가에 빼서 남은 1대로 기준을 만들 때 정상 로봇 오경보가 2/2였습니다. 정상 로봇은 3대 이상, 가능하면 5대 이상 넣으세요.

## 결과를 볼 때 주의

- `reports/`의 수치는 **로봇 단위 교차검증** 결과입니다. 학습에 쓴 로봇을 `diagnose`로 진단한 결과는 성능이 아닙니다.
- 로봇(베어링)이 적으면 수치가 크게 흔들립니다. 몇 대로 평가했는지 함께 발표하세요.
- Paderborn 데이터는 베어링 시험대 측정이라 AMR 바퀴와 조건이 다릅니다. "AMR 구동부와 같은 회전체 베어링 실측으로 검증했다"까지가 정확한 표현입니다.
- 고장 정도(`fault_severity`) 라벨이 없으면 9점 눈금은 고장 창 전체의 중앙값으로 맞추고, 정지 위험 전 경고 여유는 계산하지 않습니다.
