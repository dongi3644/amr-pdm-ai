# 실측 대비 개선: 최종 시험 (가상 로봇 · 코드 점검용 · 성능 아님)

> 가상 로봇 결과입니다. 실제 로봇 성능이 아닙니다. 전류·전압은 감시용으로만 쓰고 AI 입력에 넣지 않았습니다.

## 시험 방법 (과대적합 방지)
- **같은 코드에서 설정만 바꿔** 비교했습니다.
  - 이전 설정: 튀는 값 빼기 끔 · 보정 로봇 = 이름순 뒤쪽 1/3 · 오토인코더 1개
  - 개선 설정: 튀는 값 빼기 · 보정 로봇 = 세 대마다 한 대 · 오토인코더 3개 평균
- **선택 규칙을 미리 정했습니다.**
  - 개발용 로봇(seed 3001)에서 정답률이 같거나 높고 오경보가 늘지 않으면 개선 설정을 채택합니다.
  - 1분 점수 상위 25% 지점(0.75)은 개발용에서 오경보가 0%이고 정상 최고 점수가 2점 이하일 때만 채택합니다.
- **개발용 결과:**
  - 이전과 개선이 같았습니다 (93.3%, 오경보 5%). 그래서 개선 설정을 채택했습니다.
  - 0.75는 오경보 10%, 정상 최고 5.89점이라 탈락했습니다.
- **최종 시험은 처음 보는 로봇으로 한 번만** 돌렸습니다.
  - seed 5001, 학습 80대 → 시험 85대 (지난 시험의 2배 규모)
  - 모든 로봇에 엔코더 4개와 센서 읽기 오류(샘플 하나만 튀는 값)를 넣었습니다.
  - 결과를 보고 다시 고치지 않았습니다.

## 최종 결과

| 항목 | 이전 설정 | 개선 설정 |
|---|---|---|
| **판정 정답률** | **88.2%** | 80% |
| **고장 로봇 감지율** | **86.5%** | 67.3% |
| **정상 로봇 오경보** | 9.1% (3/33) | **0% (0/33)** |
| 바닥이 바뀐 정상 로봇 오경보 | 75% (3/4) | **0% (0/4)** |
| 정지 위험 전 경고 | 56.2% | 56.2% |
| 고장 종류 정확도 | 95.5% | 96.9% |
| 오토인코더 AUC | 0.828 | 0.828 |
| 바퀴 이상 점수: 고장 창 감지 / 정상 창 오경보 | 37.6% / 4.1% | 8.1% / 0.2% |

## 해석: 개선 설정은 '감지'를 내주고 '오경보'를 없앴습니다
- 오토인코더 AUC는 0.828로 같습니다. 고장과 정상을 가르는 능력 자체는 변하지 않았습니다.
- 바뀐 것은 **3점 기준을 정하는 정상 로봇(보정용)**입니다.
  - '세 대마다 한 대' 방식에서는 바닥이 바뀐 정상 로봇이 보정용에 들어갔습니다.
  - 그래서 바퀴 이상 점수의 3점 기준이 높아졌습니다(덜 민감해짐).
  - 그 결과 바닥 오경보는 75%에서 0%로 사라졌습니다. 대신 바퀴 점수로 잡던 체결부 풀림 고장을 많이 놓쳤습니다(고장 창 감지 37.6% → 8.1%).
- 즉 **오경보와 놓침은 맞바꾸는 관계**입니다. 어느 쪽이 나은지는 데이터가 아니라 운영 목적이 정합니다.
  - 고장을 놓치는 것이 더 나쁘면 이전 방식(`CAL_SPLIT = "tail"`)
  - 쓸데없는 정지·점검이 더 나쁘면 개선 방식(`"interleave"`)
- 개발용에서는 두 설정이 같았는데 최종에서 크게 갈렸습니다. 로봇 수가 적으면(보정용 정상 로봇 몇 대) **어떤 로봇이 보정용에 들어가느냐에 따라 결과가 크게 흔들린다**는 뜻입니다.
  - 실측에서도 같은 일이 생길 수 있습니다. **정상 기록을 많이, 여러 조건으로** 남기는 것이 가장 확실한 대책입니다.

## 실측에 주는 교훈
1. 실측 성능은 **정상 기록의 다양성과 양**에 가장 크게 좌우됩니다. 바닥, 짐, 배터리, 속도를 섞어 정상 기록을 최대한 많이 남겨야 합니다.
2. `CAL_SPLIT`(감지 우선 / 오경보 우선)은 실측 교차검증에서 두 방식을 모두 돌려 보고 운영 목적에 맞게 정합니다.
3. 센서 읽기 오류 빼기(`SPIKE_K`)는 실측 주행 기록의 오류 2개를 정확히 찾았고, 깨끗한 기록에서는 아무것도 빼지 않았습니다. 그래서 켜 두는 것이 안전합니다.
4. 간헐 고장(0%)과 약한 고장은 두 설정 모두 약합니다.

## 파일
