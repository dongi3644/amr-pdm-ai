# 진행 요약 — 구성부터 실험까지 (2026-11-10 기준)

> 이 문서의 실험 수치는 **모두 가상 데이터로 코드를 점검한 결과이고, 성능이 아닙니다.**
> 아직 실측 데이터로 학습·평가한 결과는 없습니다. 발표 성능은 실측 CSV로 `python run.py train`을 돌려 나온 교차검증 수치만 씁니다.

- **주제:** 배송로봇(AMR) 구동부 고장 예지. 무엇이 고장 나는지, 정지 위험까지 몇 분 남았는지 미리 알림
- **일정:**

  | 날짜 | 내용 |
  |---|---|
  | 11/11 | 모델 마감 |
  | 11/18 | 기능 동결 |
  | 11/25 | 팀 내부 마감 |
  | 11/27 | 본선 (충남대, 발표 10분 + 질의 3분) |

- **제출물:** IR Deck, 2분 이내 시연 영상
- **원칙:**
  - 학습과 발표에는 **실측 데이터만** 씁니다.
  - 가상 데이터는 코드 점검에만 쓰고, `data/`에 넣지 않습니다.
  - 없는 값을 만들어 채우지 않습니다.

## 2. 하드웨어

| 부품 | 내용 |
|---|---|
| 차체 | 4WD 섀시 키트 (시험 로봇 1대) |
| 제어 | 아두이노 우노, 모터 드라이버 L298N (TB6612도 가능) |
| 배터리 | RC카 2S 리포 7.4 V 1500 mAh × 2개 (**한 번에 하나씩 번갈아 사용**) |
| 진동 센서 | **MPU6050 1개** (차체에 고정). 가속도 3축 + 각속도 3축 |
| 전류·전압 센서 | **INA219 1개** (배터리와 모터 드라이버 사이). 로봇 전체 전류와 배터리 전압 |
| 쓰지 않는 것 | 속도(인코더), 온도, 배터리 잔량 센서 |

인코더는 `arduino/motor_encoder_check/`로 점검할 수 있게 해 두었습니다. 실제 보드 점검은 아직 하지 않았습니다.

## 3. 데이터 기록

```
아두이노 (MPU6050 500 Hz + INA219 50 Hz) → USB 시리얼 → 실행/0_아두이노_기록.py → data/{로봇}_{날짜_시각}.csv
```

- **CSV 열:** `time, ax, ay, az, gx, gy, gz, current, voltage, robot` + 라벨 `fault_kind, fault_wheel, fault_severity` (+ 선택 `segment`)
- **라벨:**
  - 고장 종류: `unbalance`(불평형), `looseness`(체결부 풀림), `bearing`(베어링 결함), `normal`
  - 고장 바퀴: `fl`, `fr`, `rl`, `rr`
  - 고장 정도: 0~1
- **로봇 이름의 의미:** 코드는 로봇 이름이 다르면 다른 로봇으로 셉니다. 차체가 1대이므로 `R1_정상A`, `R1_불평형1`처럼 **기록마다 이름을 나눠** 여러 대처럼 씁니다. 같은 이름의 파일은 이어 붙입니다.
- **기록 시간:** 처음 5분은 그 로봇의 '평소' 기준으로 쓰므로, 한 기록은 **6분 이상**이어야 합니다. 그 5분 동안 주행·정지·회전을 섞어야 합니다.

## 4. AI 구성

```
MPU6050 6축 → 1초 창 → 특징 36개 → 구간별 정상 기준으로 z-score
   ├→ 오토인코더 → 건강 점수 (3 주의 · 6 경고 · 9 정지 위험)
   │      → 1분마다 상태 판정 (기본: 1분 점수 = 중앙값, 2번 연속일 때만 상태 변경)
   │      → 칼만 필터 → 정지 위험까지 남은 시간(분) + 90% 범위
   └→ 랜덤포레스트 → 고장 종류(+바퀴) → SHAP → 판단 근거 3개
INA219 전류·전압 (학습 없음) → 로봇마다 처음 5분과 비교 → 전류 높음 · 배터리 낮음(7.0 V) · 사용량 mAh
```

| 역할 | 방법 |
|---|---|
| 특징 | 축 6개 × (진동 크기 RMS, 첨도, 크레스트, 저·중·고주파 에너지) = 36개 |
| 정상 기준 | `per_unit`: 로봇마다 처음 5분 / `reference`: 정상 로봇들의 공통 기준 / `auto`: 자동 선택 |
| 이상 감지 (주 모델) | 오토인코더 36-24-6-24-36. 정상만 학습하고, 검증 오차가 더 줄지 않으면 멈춤 |
| 비교 모델 | z-score 평균, ECOD, Isolation Forest, PCA |
| 점수 눈금 | 정상 99.5% 지점 = 3점, 고장 정도 0.75~0.85 창 = 9점 |
| 원인 분류 | 랜덤포레스트 150그루 (잎 최소 3, 클래스 균형) + SHAP 판단 근거 |
| 남은 시간 | 칼만 필터 (수준·기울기). 잡음 값은 학습 고장 기록으로 24가지 조합 중 골라 맞춤 |

## 5. 평가 방법 (`run.py train`)

- **로봇 단위 교차검증:** 평가할 로봇을 학습에서 완전히 빼고 모델을 만든 뒤, 그 로봇을 처음부터 끝까지 진단합니다. 이것을 모든 로봇에 돌아가며 합니다.
  - 로봇이 5대 이하이면 한 대씩 빼고, 많으면 5겹으로 나눕니다.
- **채점 지표:**

  | 무엇을 보나 | 지표 |
  |---|---|
  | 1초 창의 고장/정상 구분 | AUC, 감지율, 오경보율 |
  | 로봇 단위 | 고장 로봇 감지, 정상 로봇 오경보, 정지 위험 전 경고, 경고 여유 시간 |
  | 원인 | 정확도, 혼동행렬 (그 겹에서 배운 적 없는 원인은 따로 셈) |
  | 남은 시간 | 평균 오차(분), 90% 범위 적중률 |
  | 점수 궤적 | 단조성, 추세 일치도 |

- **결과 저장:**
  - 교차검증을 마친 뒤 모든 로봇으로 최종 모델을 다시 학습해 `artifacts/`에 저장합니다.
  - 평가 결과는 `reports/`에 남습니다.
  - `diagnose`는 로봇별 1분 단위 표와 그래프를 만듭니다.

- **방법:**

- **구성:** 정상 4대, 단계별 고장 4대 (불평형 2, 체결부 풀림 1, 베어링 1)
- **교차검증 결과:**

  | 항목 | 결과 |
  |---|---|

- **고친 문제 7개:**
  1. 같은 초에 기록하면 앞 파일을 덮어씀

  3. 정지 위험 뒤에 뜬 경고도 '미리 경고'로 셈
  4. 경고 여유 시간이 1분 길게 계산됨
  5. 배운 적 없는 원인까지 원인 정확도에 넣음
  6. 건너뛴 평가와 기준 선택 이유가 화면에 안 보임
  7. 같은 경고가 파일마다 반복됨

## 8. 지금까지 알게 된 점과 한계

1. **차체가 1대뿐입니다.**
   - 기록마다 로봇 이름을 나눠도 같은 차체라, 교차검증 점수가 실제보다 좋게 나올 수 있습니다.
   - 발표에서는 "같은 로봇의 다른 기록으로 검증"이라고 밝힙니다.
2. **과대적합 위험은 데이터 쪽에 있습니다.**
   - 고장 종류마다 기록이 하나뿐이면 모델이 그 기록 하나를 외웁니다.
   - 정상과 고장 기록이 날짜, 바닥, 배터리, 기록 길이에서 다르면 그 차이를 고장으로 배웁니다.
3. **센서가 1개라 어느 바퀴인지는 구분이 약합니다.** 가상 시험에서는 고장 종류 정확도가 90% 이상이었지만, 바퀴까지 맞힌 비율은 72%였습니다.
4. **간헐 고장과 센서에서 먼 바퀴의 체결부 풀림이 가장 어렵습니다.**
5. **학습에 없던 고장은 '이상하다'까지는 알아채지만 원인은 틀릴 수 있습니다.**
6. **배터리를 번갈아 쓰면 조심할 점이 두 가지 있습니다.**
   - A·B 배터리를 정상과 고장 기록에 골고루 써야 합니다. 한쪽에 몰리면 배터리 차이를 고장으로 배울 수 있습니다.
   - 같은 로봇 이름으로 배터리를 바꿔 이어 기록하면 mAh 사용량이 이어서 더해집니다.
7. **가상 정상 로봇은 실제보다 얌전합니다.** 오경보 0%나 높은 정답률을 실측에 그대로 기대하면 안 됩니다.

| 실제 보드로 기록기 시험 | 기록 스케치와 모터·인코더 점검 스케치를 아직 실제 보드에서 돌려 보지 않음 |
| 실측 기록 | 정상 3개 이상 + 고장 종류마다 2개 이상. 정상과 고장을 같은 날, 같은 바닥, 같은 길이로. 배터리 A·B 골고루. 시연용 기록은 따로 보관 |
| 실측 학습·평가 | `python run.py train` → 교차검증 수치 = 발표 성능 |
| 판정 설정 결정 | 실측 정상 기록에서 1분 점수가 얼마나 흔들리는지 보고 `PERIOD_QUANTILE`(0.5 또는 0.75) 결정. 정한 뒤 시연용 기록으로 한 번만 확인 |
| 선택 | 배터리 교체를 자동으로 알아채 mAh 사용량을 새로 세는 기능, 기록 계획 체크리스트 |
