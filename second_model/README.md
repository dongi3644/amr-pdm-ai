# second_model — AMR 구동부 고장 예지 AI (최종 정리본)

이 폴더의 **코드와 이 문서만 보면** 모델이 어떻게 동작하는지, 실측 데이터로 어떻게 돌리는지, 무엇을 바꿀 수 있는지 알 수 있게 정리했습니다.
`amr_pdm_real/`은 그동안 시험하며 쌓인 기록이고, 코드는 이 폴더와 같습니다 (2026-11-11 기준 최종 설정).

> 이 문서의 성능 숫자는 모두 **가상 로봇**으로 잰 값입니다. 발표 성능은 실측 CSV로 `python run.py train`을 돌려 나온 **교차검증 수치만** 씁니다.

---

## 1. 한눈에 보기

배송로봇(AMR)의 진동·바퀴 속도를 보고 **고장이 났는지, 무슨 고장인지(어느 바퀴), 정지 위험까지 몇 분 남았는지** 알려 줍니다.
전류·전압은 AI와 따로 **감시용**(전류 높음, 배터리 낮음, 사용량 mAh)으로만 씁니다.

```
CSV (시간, 가속도·각속도 6축, 엔코더 4개, 모터 명령, 전류, 전압, 라벨)
 │
 ├─ AI (학습)
 │    1초 창 → 특징 47개 (진동 36 + 바퀴 11) → 로봇마다 '평소'와 비교한 z값
 │      ├→ 오토인코더 점수 ┐
 │      └→ 바퀴 이상 점수 ┴→ 큰 쪽 = 건강 점수 (3 주의 · 6 경고 · 9 정지 위험)
 │                           → 1분마다 상태 판정 (2번 연속일 때만 바뀜)
 │                           → 칼만 필터: 정지 위험까지 남은 분
 │      └→ 랜덤포레스트: 고장 종류 + 바퀴, SHAP: 판단 근거 3개
 │
 └─ 감시 (학습 없음): 전류가 평소(처음 5분)보다 높음 · 배터리 7.0 V 아래 · 사용량 mAh
```

## 3. 수집해야 할 데이터

### 3-1. CSV 열 (한 줄 = 샘플 하나, 약 500 Hz)

| 열 | 필수 | 알아듣는 이름·단위 (자동 변환) |
|---|---|---|
| 시간 | ✅ | `time`(초), `시간`, `t_us`·`micros`(µs), `t_ms`(ms), `시간(us)` 등 |
| 가속도 3축 | ✅ | `ax, ay, az` — g 또는 센서 원래 정수값(÷8192) |
| **각속도 3축** | ✅ | `gx, gy, gz` — °/s 또는 원래값(÷65.5). **없으면 학습·진단 불가** |
| 엔코더 4개 | 권장 | `enc1~enc4`, `엔코더1~4`, `enc_fl…` — 누적 펄스 / 샘플마다 센 펄스 / 속도 자동 판단. 1 앞왼 · 2 앞오른 · 3 뒤왼 · 4 뒤오른 |
| 모터 명령 | 권장 | `cmd`, `pwm`, `spd`, `모터명령` |
| 전류, 전압 | 권장 | `mA`, `mV`, `전류(mA)`, `current`, `voltage` (감시용) |
| 로봇 이름 | 권장 | `robot` — 같은 이름의 파일은 이어 붙임. 없으면 파일 이름이 로봇 이름 |
| 고장 라벨 | 고장 기록에 | `label`/`fault_kind`(normal·idle, unbalance, looseness, bearing), `fault_wheel`(fl·fr·rl·rr), `fault_severity`(0~1) |
| 구간 | 선택 | `segment` — 장소·노면 이름 (바닥이 바뀌는 곳 구분) |

### 3-2. 기록 목록 (최소 권장)

| 기록 | 개수 | 길이 | 방법 |
|---|---|---|---|
| **정상** | **3개 이상 (많을수록 좋음)** | 10분 이상 | 다른 날·바닥·짐·배터리 A/B·속도로. **실측 성능에 가장 큰 영향** |
| 고장: 불평형 | 2개 이상 | 15분 이상 | 처음 5분은 고장 없이 → 고장을 내고 계속 기록 |
| 고장: 체결부 풀림 | 2개 이상 | 15분 이상 | 같은 방식. 어느 바퀴인지 `fault_wheel`에 |
| 고장: 베어링 결함 | 2개 이상 | 15분 이상 | 같은 방식 |
| 시연용 | 1~2개 | 10분 이상 | **처음부터 따로 보관**, 마지막에 한 번만 진단 |

기록 규칙:
- 한 기록은 **6분 이상** (처음 5분 = 그 로봇의 '평소' 기준, 판정하지 않음). 처음 5분에 전진·정지·회전·후진을 섞을 것
- 정상과 고장 기록은 **같은 날·같은 바닥·비슷한 길이**로 (다르면 그 차이를 고장으로 배움)
- 센서 붙인 자세를 바꾸지 말 것 (바꿨으면 새 로봇 이름으로 기준을 다시)
- 엔코더 4개가 **모든 기록에** 있어야 바퀴 특징이 켜짐

## 5. 설정 (`config.py`)

### 5-1. 실측 전에 꼭 맞출 값

| 설정 | 지금 | 뜻 |
|---|---|---|
| `RAW_ACCEL_LSB_PER_G` | 8192 | 가속도 원래값 ÷ 이 값 = g (스케치 범위 ±2g 16384 · ±4g 8192 · ±8g 4096) |
| `RAW_GYRO_LSB_PER_DPS` | 65.5 | 각속도 원래값 ÷ 이 값 = °/s (±250°/s **131** · ±500 65.5 · ±1000 32.8). 스케치가 범위를 안 바꿨다면 131 |
| `COLUMN_ALIASES`의 `enc_fl`~`enc_rr` | 1~4번 | 엔코더 번호 ↔ 바퀴 위치. 배선이 다르면 목록을 바꿀 것 |
| `ENCODER_MODE` | "auto" | 엔코더 값 종류 (counter·increment·speed). `check`에 나온 판단이 틀리면 직접 정함 |
| `BATTERY_CAPACITY_MAH`, `BATTERY_LOW_V` | 1500, 7.0 | 배터리 용량, '배터리 낮음' 기준 |

### 5-2. 최종 설정 (가상 시험에서 가장 높았던 조합)

| 설정 | 값 | 뜻 |
|---|---|---|
| `ENCODER_FEATURES` | "auto" | 모든 학습 기록에 엔코더 4개가 살아 있으면 바퀴 특징 11개 사용 |
| `WHEEL_SCORE` | True | 바퀴 이상 점수(한 바퀴만 튀는 정도)를 오토인코더 점수와 함께 사용 |
| `CAL_SPLIT` | "tail" | 3점 눈금을 정하는 정상 로봇 = 이름순 뒤쪽 1/3 → **고장 감지 우선** |
| `AE_ENSEMBLE` | 1 | 오토인코더 개수 |
| `SPIKE_K` | 0 (끔) | 센서 읽기 오류(샘플 하나만 튀는 값) 빼기 |
| `PERIOD_S` / `PERIOD_QUANTILE` / `CONFIRM_PERIODS` | 60 / 0.5 / 2 | 1분마다, 1초 점수의 중앙값으로, 2번 연속일 때 상태 변경 |
| `BASELINE_PERIODS` | 5 | 처음 5분 = 정상 기준 |
| `THRESH` | 3 / 6 / 9 | 주의 / 경고 / 정지 위험 점수 |
| `HEARTBEAT_S` | 300 | 실행 중 '학습 중'·'평가 중'을 다시 알리는 간격[초] (시작할 때는 바로 한 번) |

### 5-3. 실측에서 성능이 낮을 때 바꿔 볼 값

**한 번에 하나만** 바꾸고, `train`의 **교차검증**으로 비교, **2~3번 안에서** 정할 것 (많이 바꿔 볼수록 그 데이터에 맞춰지는 과대적합). 시연용 기록으로는 비교하지 말 것.

| 증상 | 바꿔 볼 것 (위가 먼저) | 대가 |
|---|---|---|
| **오경보가 많음** | ① 정상 기록을 여러 조건으로 추가 (가장 효과 큼) | — |
| | ② 바닥이 바뀌는 곳이면 `segment` 기록, 또는 `CAL_SPLIT = "interleave"` | 고장 감지도 줄 수 있음 |
| | ③ `WHEEL_SCORE = False` | 한 바퀴 고장 감지가 줄어듦 |
| | ④ `check`에 튀는 값 경고가 많으면 `SPIKE_K = 8` | — (실제 충격은 안 뺌) |
| | ⑤ `CONFIRM_PERIODS = 3` | 경보가 1분 늦어짐 |
| **고장을 놓침** | ① diagnose 그래프에서 고장이 점수에 드러나는지, 엔코더 4개가 다 사는지 확인 | — |
| | ② `CAL_SPLIT = "tail"` (지금 값) 유지 | 오경보가 조금 늘 수 있음 |
| | ③ 간헐 고장이면 `PERIOD_QUANTILE = 0.75` | 오경보가 늘 수 있음 |
| | ④ `CONFIRM_PERIODS = 1` 또는 `PERIOD_S = 30` | 오경보가 늘어남 |
| **경고가 늦음** | `FAIL_CAL_BAND` 낮게(예: 0.65~0.75), `THRESH["warning"]` 6 → 5 | '정지 위험'의 뜻이 바뀜 |
| **원인을 틀림** | 고장 종류마다 기록 2개 이상, 엔코더 4개 확보 | — |
| **기록마다 결과가 들쭉날쭉** | `BASELINE_PERIODS` 5 → 7~10, `AE_ENSEMBLE = 3` | 기록이 길어야 함 / 학습이 느려짐 |

**바꾸지 말 것:** `SCORE_MAX`, `MIN_FAIL_RATIO`, 오토인코더 크기(24-6-24)·원인 분류 나무 설정 — 키우면 학습 데이터를 외우기 쉬워짐.
값을 바꾸면 **`train`부터 다시** (판정 주기·1분 점수 방식·연속 횟수는 모델 파일에 저장되어 진단에 그대로 쓰임).

## 6. 모델이 동작하는 방식 (자세히)

1. **읽기** (`dataio.py`): 단위를 맞추고(µs→초, 원래값→g·°/s, mA→A), 엔코더 값을 누적 펄스로 바꾸고, **엔코더 4개의 상태**(정상·죽음·도중에 멈춤)를 판정합니다. 죽은 엔코더는 없는 것으로 처리합니다. 1초씩 자릅니다.
2. **특징** (`features.py`): 1초마다
   - 진동 36개 = 6축 × (진동 크기 RMS, 첨도, 크레스트, 저·중·고주파 에너지)
   - 바퀴 11개 (엔코더 4개가 있을 때) = 바퀴 4개 × (상대 속도: 다른 세 바퀴보다 빠르거나 느린 비율, 속도 흔들림: 다른 바퀴와 다르게 출렁이는 정도) + 왼쪽·오른쪽 앞뒤 속도 차이 + 모터 명령 대비 속도. **바퀴가 실제로 도는 구간만**으로 계산
3. **정상 기준** (`models.SegmentBaseline`): 로봇마다 처음 5분의 평균·표준편차 → 이후 1초를 "평소보다 몇 배 벗어났나"(z)로 바꿈
4. **이상 점수**:
   - 오토인코더: 정상 z만으로 학습한 신경망(47→24→6→24→47)이 복원하지 못한 정도
   - 바퀴 이상 점수: 네 바퀴 중 **한 바퀴만 외톨이처럼** 벗어난 정도 (네 바퀴가 함께 흔들리는 바닥 영향은 작게 나옴)
   - 두 점수를 각각 "학습에 안 쓴 정상 로봇의 99.5% = 3점, 고장 정도 0.75~0.85 = 9점" 눈금에 맞춘 뒤 **큰 쪽**이 건강 점수
5. **판정** (`infer.py`): 1분마다 1초 점수의 중앙값 → 3점 미만 정상, 6점 미만 주의, 그 이상 경고. **2번 연속**일 때만 상태 변경(9점 이상은 바로)
6. **원인**: 주의 이상일 때 랜덤포레스트가 고장 종류·바퀴 확률을 내고, SHAP으로 판단 근거 3개
7. **남은 시간**: 칼만 필터가 1분 점수의 추세로 9점(정지 위험)까지 남은 분과 90% 범위를 예측 (잡음 값은 학습 고장 기록으로 맞춤)
8. **전류·배터리** (`power.py`): AI와 별도. 처음 5분 대비 전류가 높은 상태가 2분 연속이면 '전류 높음', 7.0 V 아래면 '배터리 낮음', 사용량 mAh

## 7. 가상 데이터 성능과 이유

### 7-1. 최종 코드의 가상 성능 (처음 보는 가상 로봇, 엔코더 4개 있음)

| 시험 | 판정 정답률 | 고장 감지율 | 정상 오경보 | 정지 위험 전 경고 | 고장 종류 정확도 |
|---|---|---|---|---|---|
| ① 45대 | **91.1%** | **89.3%** | 5.9% | 92.9% | 96% |
| ② 85대 (센서 읽기 오류 포함, 더 어려움) | **88.2%** | **86.5%** | 9.1% | 56.2% | 95.5% |

약한 경우: 간헐 고장(가끔만 나타남) 0%, 약한 고장 약 50%, 바닥이 바뀐 정상 로봇의 오경보.

### 7-2. 어떻게 튜닝해서 올라갔나

| 단계 | 바꾼 것 | 정답률 | 비고 |
|---|---|---|---|
| 0 | 진동만 (특징 36개) | 82.2% | 가벼운 시험 |
| 1 | 엔코더 바퀴 특징 추가 | 73.3% ↓ | 멈추거나 출발할 때 0 근처 속도로 나눠 값이 튐 → 정상도 이상처럼 보임 |
| 2 | **바퀴가 도는 구간만** 계산 | 86.7% | 가벼운 시험 |
| 3 | (2번을 시험 ①에서 측정) | **80.0%** | 시험 ① 개선 전 |
| 4 | **바퀴 상대 속도** + **바퀴 이상 점수**(큰 쪽 사용) | 91.1% | 개발용 · 바닥 오경보 2/2 |
| 5 | 가장 튄 바퀴 − 네 바퀴 중앙값 | 93.3% | 개발용 · 바닥 오경보 1/2 |
| 6 | 네 바퀴 흩어짐으로 나눔 (외톨이 점수) | 93.3% | 개발용 · 최종 |
| 7 | 6번을 시험 ①에 **한 번만** | **91.1%** | 시험 ① 개선 후 (고장 감지 67.9% → 89.3%) |

효과가 없거나 나빴던 것: 학습 로봇 4배(+1%p), 1분 점수 상위 25% 지점(오경보 증가), 오토인코더 3개 평균·튀는 값 빼기·보정 로봇 고루 섞기(오경보는 0%가 됐지만 정답률 80%로 하락 → 끔).

**왜 올라갔나:** 데이터·모델을 키운 것이 아니라, **"바퀴 고장은 한 바퀴에만 생기고, 주행 상태·바닥은 네 바퀴 모두에 영향을 준다"**는 차이를 점수로 만든 것이 핵심입니다.
- 바퀴 속도 자체는 주행·정지·회전에 따라 크게 변함 → **상대 속도**로 주행 영향을 지움
- 오토인코더는 47개 특징을 평균 내서 바퀴 하나의 이상이 묻힘 → **바퀴 이상 점수**를 따로 봄
- 바닥이 거칠면 네 바퀴가 함께 흔들림 → **외톨이 점수**로 공통 흔들림을 지움

**과대적합 방지:** 개발용 가상 로봇(seed 3001)으로만 고르고, 처음 보는 시험 로봇에는 한 번만 돌렸습니다. 개발용 93.3% ↔ 시험 91.1%로 비슷합니다.

### 7-3. 왜 가상에서는 성능이 좋게 나왔나 (실측은 더 낮을 가능성이 큼)

| 가상 데이터 | 실측에서 |
|---|---|
| 고장이 바퀴 속도·진동에 주는 영향을 **사람이 식으로 정함** (베어링 15% 느려짐 등) | 실제 고장이 엔코더에 그만큼 드러나는지 모름 |
| 정상 로봇이 얌전함 (잡음이 일정) | 바닥·배터리·온도·미끄러짐으로 정상 점수가 더 흔들림 → 오경보 또는 놓침 증가 |
| 로봇 수십 대 | 차체 1대 (교차검증이 좋게 나와도 다른 로봇에 통한다는 증거는 아님) |
| 고장 정도 라벨이 정확 | 사람이 정하는 값이라 흔들림 → 9점 눈금·남은 시간 부정확 |
| 엔코더 깨끗 | 해상도·빠진 펄스·미끄러짐 |

그래도 "고장 난 바퀴는 다른 바퀴와 다르게 돈다"는 원리는 실제 물리 현상이라 **엔코더를 쓰는 방향은 실측에서도 도움이 될 가능성이 높습니다.** 얼마나인지는 실측 교차검증으로만 알 수 있습니다.

## 8. 주의할 점

- **결과를 보고 설정을 여러 번 바꾸지 말 것** (과대적합). 시연용 기록은 마지막에 한 번만
- 발표에는 **실측 교차검증 수치만**. 가상 수치는 코드 점검용
- 엔코더로 학습한 모델은 진단할 기록에도 엔코더 4개가 있어야 함 (없으면 알려 줌)
- `check`의 **엔코더 상태**: '죽음'이면 그 엔코더를 빼고(4개 미만이면 진동만으로 진단), '도중에 멈춤'이면 선 빠짐 의심 → 바퀴 고장이 아니라 센서 이상일 수 있음
- 배터리 A/B를 정상·고장 기록에 골고루. 같은 로봇 이름으로 배터리를 바꿔 이어 기록하면 mAh가 이어서 더해짐
- 가상 시험(코드 점검, 성능 아님, 결과는 `가상테스트_결과/README.md`):
  - 빠른 확인 약 4분: `python 가상테스트/test_complex.py --scale 0.1 --encoders`
  - 학습 약 10분 + 시험 약 10분: `python 가상테스트/test_complex.py --train-scale 0.45 --test-scale 0.5 --encoders` (가상 기록 만들기 몇 분 별도. VS Code 목록에도 있음)
  - `--train-scale`·`--test-scale`로 학습·시험 로봇 수를 따로 정함 (시험 로봇은 학습과 다른 seed로 만들어 겹치지 않음)
