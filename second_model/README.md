# second_model — AMR 구동부 고장 예지 AI (최종 정리본)

이 폴더의 **코드와 이 문서만 보면** 모델이 어떻게 동작하는지, 실측 데이터로 어떻게 돌리는지, 무엇을 바꿀 수 있는지 알 수 있게 정리했습니다.
`amr_pdm_real/`은 그동안 시험하며 쌓인 기록입니다. **새 수정은 이 폴더(`second_model/`)에만** 합니다.

> 이 문서의 성능 숫자는 모두 **가상 로봇**으로 잰 값입니다. 발표 성능은 실측 CSV로 `python run.py train`을 돌려 나온 **교차검증 수치만** 씁니다.

---

## 1. 한눈에 보기

배송로봇(AMR)의 진동·바퀴 속도를 보고 **고장이 났는지, 무슨 고장인지(어느 바퀴), 얼마나 위험한지(고장 위험도 %)** 알려 줍니다.
전류·전압은 AI와 따로 **감시용**(전류 높음, 배터리 낮음, 사용량 mAh)으로만 씁니다.

```
CSV (시간, 가속도·각속도 6축, 엔코더 4개, 모터 명령, 전류, 전압, 라벨)
 │
 ├─ AI (학습)
 │    1초 창 → 특징 47개 (진동 36 + 바퀴 11) → 로봇마다 '평소'와 비교한 z값
 │      ├→ 오토인코더 점수 (정상만 학습: 처음 보는 고장)       ┐
 │      ├→ 랜덤포레스트 점수 (고장 데이터가 있을 때: 아는 고장) ├→ 가장 큰 값 = 건강 점수 (3 경미 · 6 심각 · 9 = 위험도 100%)
 │      └→ 바퀴 이상 점수 (엔코더 4개가 있을 때)               ┘
 │                           → 1분마다 상태 판정 (1분 점수 = 1초 점수의 상위 25% 지점이 2점 이상인 주기가 2번 연속이면 경미, 11/19)
 │      └→ 랜덤포레스트: 고장 종류 + 바퀴, SHAP: 판단 근거 3개
 │
 └─ 감시 (학습 없음): 전류가 평소(처음 5분)보다 높음 · 배터리 7.0 V 아래 · 사용량 mAh
```

## 3. 수집해야 할 데이터

### 3-1. CSV 열 (한 줄 = 샘플 하나, 약 500 Hz)

| 열 | 필수 | 알아듣는 이름·단위 (자동 변환) |
|---|---|---|
| 시간 | ✅ | `time`(초), `시간`, `t_us`·`micros`(µs), `t_ms`(ms), `시간(us)` 등 |
| 가속도 3축 | ✅ | `ax, ay, az` — g 또는 센서 원래 정수값(÷8192) |
| **각속도 3축** | ✅ (없으면 엔코더로) | `gx, gy, gz` — °/s 또는 원래값(÷65.5). **열이 없으면 좌우 엔코더로 `gz`(회전 속도)만 계산**하고 `gx, gy`는 빼고 학습 (아래 '각속도 열이 없을 때') |
| 엔코더 4개 | 권장 | `enc1~enc4`, `엔코더1~4`, `enc_fl…` — 누적 펄스 / 샘플마다 센 펄스 / 속도 자동 판단. 1 앞왼 · 2 앞오른 · 3 뒤왼 · 4 뒤오른 |
| 모터 명령 | 권장 | `cmd`, `pwm`, `spd`, `모터명령` |
| 전류, 전압 | 권장 | `mA`, `mV`, `전류(mA)`, `current`, `voltage` (감시용) |
| 로봇 이름 | 권장 | `robot` — 같은 이름의 파일은 이어 붙임. 없으면 파일 이름이 로봇 이름 |
| 고장 라벨 | 고장 기록에 | `label`/`fault_kind`(normal·idle, unbalance, looseness, bearing), `fault_wheel`(fl·fr·rl·rr), `fault_severity`(0~1) |
| 구간 | 선택 | `segment` — 장소·노면 이름 (바닥이 바뀌는 곳 구분) |

시리얼 출력을 그대로 저장해도 됩니다: 머리줄 앞의 상태 문구(`shield ok`, `ina ok`), 중간의 `MPU FAIL`·`MPU ZERO`·`#`로 시작하는 줄·다시 찍힌 머리줄·칸이 넘치는 깨진 줄은 자동으로 건너뛰고 `check`의 '확인할 점'에 몇 줄인지 알려 줍니다.

### 3-2. 기록 목록 (최소 권장)

| 기록 | 개수 | 길이 | 방법 |
|---|---|---|---|
| **정상** | **3개 이상 (많을수록 좋음)** | 10분 이상 | 다른 날·바닥·짐·배터리 A/B·속도로. **실측 성능에 가장 큰 영향** |
| 고장: 바퀴 불균형·변형 (`unbalance`) | 2개 이상 | 15분 이상 | 처음 5분은 고장 없이 → 고장을 내고 계속 기록 |
| 고장: 체결 풀림 (`looseness`) | 2개 이상 | 15분 이상 | 같은 방식. 어느 바퀴인지 `fault_wheel`에 |
| 고장: 마찰 증가 (베어링·걸림, `bearing` 또는 `friction`) | 2개 이상 | 15분 이상 | 같은 방식 |
| 시연용 | 1~2개 | 10분 이상 | **처음부터 따로 보관**, 마지막에 한 번만 진단 |

기록 규칙:
- 한 기록은 **6분 이상** (처음 5분 = 그 로봇의 '평소' 기준, 판정하지 않음). 처음 5분에 전진·정지·회전·후진을 섞을 것
- 정상과 고장 기록은 **같은 날·같은 바닥·비슷한 길이**로 (다르면 그 차이를 고장으로 배움)
- 센서 붙인 자세를 바꾸지 말 것 (바꿨으면 새 로봇 이름으로 기준을 다시)
- 엔코더 4개가 **모든 기록에** 있어야 바퀴 특징이 켜짐

**각속도 열이 없을 때** (`config.GYRO_FROM_ENCODERS = True`, 기본)
- 왼쪽(enc1·enc3 중 하나 이상)·오른쪽(enc2·enc4 중 하나 이상) 엔코더로 `gz [°/s] = (오른쪽 속도 − 왼쪽 속도) ÷ 바퀴 사이 거리`를 계산. `check` 표의 '각속도' 칸에 **gz만 엔코더로 계산**이라고 나옴
- `gx, gy`(좌우·앞뒤 기울어짐)는 바퀴로 알 수 없어 만들지 않음 → 진동 특징 36개 중 24개(ax·ay·az·gz)만 씀. 기록 하나라도 각속도가 없으면 모든 기록에서 gx·gy를 뺌
- 엔코더 속도는 0.1초 단위라 빠른 떨림은 담기지 않음 (진동은 가속도가 맡음). 가상 시험: 6축 + 엔코더와 거의 같은 결과 (`가상테스트_결과/센서비교/README.md`)
- 좌우 모터가 거울처럼 달려 오른쪽 펄스가 반대로 세지면 자동으로 뒤집고 '확인할 점'에 알림 (`ENCODER_RIGHT_SIGN`)
- 각속도 없이 학습한 모델로 각속도가 있는 기록을 진단하는 것은 됨. 반대(6축으로 학습 → 각속도 없는 기록 진단)는 오류로 알려 줌

## 4. 실행 순서

### VS Code에서 (GitHub에서 받은 코드)
1. `git clone https://github.com/dongi3644/amr-pdm-ai.git` (또는 GitHub `Code` → `Download ZIP`)
2. VS Code `파일 → 폴더 열기` → `amr-pdm-ai` 또는 `amr-pdm-ai/second_model` (어느 쪽을 열어도 실행 목록이 나옴). 확장 설치 안내가 뜨면 `설치` (Python, Python Debugger). F5를 눌렀는데 "Select a debug configuration" 창(Python File, Django …)만 뜨면 다른 폴더가 열린 것 → Esc 후 폴더를 다시 열기
3. 왼쪽 `실행 및 디버그`(Ctrl+Shift+D) 목록에서 **1. 환경 설치** ▶ (처음 한 번) → **2 → 3 → 4** 순서로 ▶
4. 실행 중에는 아래 터미널에 **지금 하는 작업이 처음 한 번, 그 뒤 5분마다** 나옵니다 (`config.HEARTBEAT_S`)
   ```
   [14:03:10] ▶ 평가 중 (로봇 단위 교차검증: 겹마다 평가 로봇을 빼고 학습 → 그 로봇 진단)
   [14:08:10] 평가 중 (로봇 단위 교차검증: …) (5분 경과)
   [14:11:42] ▶ 학습 중 (최종 모델: 모든 로봇)
   [14:12:30] ■ 끝: 학습 중 (최종 모델: 모든 로봇) (전체 9.3분)
   ```

### 터미널에서 (`second_model` 폴더)
처음 한 번: `python 실행/1_환경설치.py` → 아래 명령

| 순서 | 명령 | 하는 일 | 볼 것 |
|---|---|---|---|
| 1 | CSV를 `data/`에 넣기 | | 시연용 기록은 넣지 말 것 |
| 2 | `python run.py check` | 형식 검사 | 로봇별 표(길이·샘플링·엔코더 n/4 동작·라벨), **확인할 점**(단위 변환, 튀는 값, 죽은 엔코더), 엔코더 상태 표 |
| 3 | `python run.py train` | 로봇 단위 교차검증 → 최종 모델 학습 | `reports/summary.md`·`metrics.json`·그래프 = **발표 성능**, `artifacts/model_bundle.joblib` = 최종 모델 |
| 4 | `python run.py diagnose` | 로봇별 1분 단위 진단 | 화면: 로봇마다 지금 단계·위험도 %·알림(예: `8분 심각 (위험도 74%)`)·할 일. `reports/diagnose/<로봇>.csv·png` (건강 점수, 고장 위험도 %, 단계, 지금 상황, 할 일, 원인, 고장 부위, 전류, 배터리, 배선, 바퀴 속도) |
| 5 | `python run.py diagnose --path 시연폴더` | 시연용 기록 진단 (한 번만) | "처음 보는 로봇"으로 표시되면 학습에 안 쓴 기록 |

옵션: `--path 폴더`, `--fs 500`(time 열이 없을 때), `--period-s 60`, `--baseline auto|per_unit|reference`, `train --no-eval`(교차검증 생략)

**정상 데이터만으로 학습해서 쓰기 (11/15, 정상 데이터 40개 = 10~20초씩 8.7분, 예전 스케치)**
1. 정상 CSV를 `data/`에 넣고 `train` → 기록이 짧아 '공통 기준(reference)'이 자동 선택됨 → `live`는 처음 5분 배우기 없이 **바로 판정**
2. 각속도 열이 없고 엔코더도 1개면 **가속도 3축만**으로 학습 (11/15부터 오류 대신 진행)
3. segment 열이 없고 `spd`가 0~9 같은 단계면 **속도 단계마다 정상 기준을 따로** 만듦 (`SEGMENT_FROM_MOTOR_CMD`). 이 로봇은 진동 크기가 속도 0 → 9에서 0.005 → 0.84 g로 달라져, 섞으면 고장에 둔해짐
4. 고장 데이터가 없으면 3점(경미) 눈금 = 처음 보는 정상 기록의 10초 중앙값 최댓값 × 1.2 (`NORMAL_ONLY_BLOCK`·`NORMAL_ONLY_MARGIN`). 1초 99.5% 눈금은 보정 창이 적으면 '가장 튄 1초'가 되어 너무 높아짐 (4.22 → 0.91×1.2)
- 시험 (정상 기록 재생, 가상 고장 = 정상 기록에 12 Hz 흔들림을 더한 것): 정상 8.7분·4분 → 끝까지 **정상** / 흔들림 0.5 g → 3분째 **고장(경미)** / 0.35 g → 위험도 21%로 정상
- **한계:** 지금 정상 데이터로는 평소보다 꽤 큰 변화(위 시험에서 약 0.5 g)여야 고장으로 잡습니다. 같은 속도로 몇 분씩 이어서 기록한 정상 데이터가 늘수록 민감해집니다 (`run.py live`가 받은 데이터를 저장하므로 그것을 `data/`에 넣고 다시 `train`)
- 학습에 없는 속도 단계로 달리면 전체 기준과 비교해 덜 정확합니다 (지금: 0·3·5·7·8·9). 스케치 설정(저역필터 등)도 정상 데이터를 기록할 때와 같아야 합니다

| `ENCODER_FEATURES` | "auto" | 모든 학습 기록에 엔코더 4개가 살아 있으면 바퀴 특징 11개 사용 |
| `WHEEL_SCORE` | True | 바퀴 이상 점수(한 바퀴만 튀는 정도)를 오토인코더 점수와 함께 사용 |
| `CAL_SPLIT` | "tail" | 3점 눈금을 정하는 정상 로봇 = 이름순 뒤쪽 1/3 → **고장 감지 우선** |
| `AE_ENSEMBLE` | 1 | 오토인코더 개수 |
| `SPIKE_K` | 0 (끔) | 센서 읽기 오류(샘플 하나만 튀는 값) 빼기 |
| `PERIOD_S` / `PERIOD_QUANTILE` / `CONFIRM_PERIODS` | 60 / 0.75 / 2 | 1분마다, 1초 점수의 상위 25% 지점으로, 2번 연속일 때 상태 변경 (11/19, [final.md](../final.md)) |
| `CAUTION_ALARM` | 2.0 | 경미 경보를 내는 1분 점수 (눈금 3점 = 정상 99.5%는 그대로, 문턱만 2점. 11/19, [final.md](../final.md)) |
| `CAUSE_WINDOW` / `CAUSE_BY_KIND` | 180 / True | 원인 확률을 최근 180창(3분) 평균, 종류별로 바퀴 확률을 더해 종류 먼저 (11/19: 60 / False에서 바꿈) |
| `RF_DETECTOR` | True | 고장 라벨이 있으면 랜덤포레스트 이상 점수를 더해 오토인코더·랜덤포레스트(·바퀴) 중 큰 값을 건강 점수로 (11/18). 라벨이 없으면 오토인코더(+바퀴)만 |
| `BASELINE_PERIODS` | 5 | 처음 5분 = 정상 기준 |
| `THRESH` | 3 / 6 / 9 | 경미 시작 / 심각 시작 / 위험도 100%(학습한 고장 기준) 점수 |
| `HEARTBEAT_S` | 300 | 실행 중 '학습 중'·'평가 중'을 다시 알리는 간격[초] (시작할 때는 바로 한 번) |

### 5-3. 실측에서 성능이 낮을 때 바꿔 볼 값

**한 번에 하나만** 바꾸고, `train`의 **교차검증**으로 비교, **2~3번 안에서** 정할 것 (많이 바꿔 볼수록 그 데이터에 맞춰지는 과대적합). 시연용 기록으로는 비교하지 말 것.

| 증상 | 바꿔 볼 것 (위가 먼저) | 대가 |
|---|---|---|
| **오경보가 많음** | ① 정상 기록을 여러 조건으로 추가 (가장 효과 큼) | — |
| | ② 바닥이 바뀌는 곳이면 `segment` 기록, 또는 `CAL_SPLIT = "interleave"` | 고장 감지도 줄 수 있음 |
| | ③ `WHEEL_SCORE = False` | 한 바퀴 고장 감지가 줄어듦 |
| | ④ `check`에 튀는 값 경고가 많으면 `SPIKE_K = 8` | — (실제 충격은 안 뺌) |
| | ⑤ `CAUTION_ALARM = 3.0` (11/19 전 값) | 약한 고장을 놓침 (L1 감지 90% → 62%) |
| **고장을 놓침** | ① diagnose 그래프에서 고장이 점수에 드러나는지, 엔코더 4개가 다 사는지 확인 | — |
| | ② `CAL_SPLIT = "tail"` (지금 값) 유지 | 오경보가 조금 늘 수 있음 |
| | ③ 그 고장 종류의 기록을 학습에 넣기 (`RF_DETECTOR`가 바로 배움) | — |
| | ④ `CONFIRM_PERIODS = 1` 또는 `PERIOD_S = 30` | 오경보가 늘어남 (검증: 1번이면 3.8%) |
| **심각이 늦음** | `FAIL_CAL_BAND` 낮게(예: 0.65~0.75), `THRESH["warning"]` 6 → 5 | '위험도 100%'의 뜻이 바뀜 |
| **원인을 틀림** | 고장 종류마다 기록 2개 이상, 엔코더 4개 확보 | — |
| **기록마다 결과가 들쭉날쭉** | `BASELINE_PERIODS` 5 → 7~10, `AE_ENSEMBLE = 3` | 기록이 길어야 함 / 학습이 느려짐 |

**바꾸지 말 것:** `SCORE_MAX`, `MIN_FAIL_RATIO`, 오토인코더 크기(24-6-24)·원인 분류 나무 설정 — 키우면 학습 데이터를 외우기 쉬워짐.
값을 바꾸면 **`train`부터 다시** (판정 주기·1분 점수 방식·연속 횟수는 모델 파일에 저장되어 진단에 그대로 쓰임).

## 6. 모델이 동작하는 방식 (자세히)

1. **읽기** (`dataio.py`): 단위를 맞추고(µs→초, 원래값→g·°/s, mA→A), 엔코더 값을 누적 펄스로 바꾸고, **엔코더 4개의 상태**(정상·죽음·도중에 멈춤)를 판정합니다. 죽은 엔코더는 없는 것으로 처리합니다. 1초씩 자릅니다.
2. **특징** (`features.py`): 1초마다
   - 진동 36개 = 6축 × (진동 크기 RMS, 첨도, 크레스트, 저·중·고주파 에너지)
   - 바퀴 11개 (엔코더 4개가 있을 때) = 바퀴 4개 × (상대 속도: 다른 세 바퀴보다 빠르거나 느린 비율, 속도 흔들림: 다른 바퀴와 다르게 출렁이는 정도) + 왼쪽·오른쪽 앞뒤 속도 차이 + 모터 명령 대비 속도. **바퀴가 실제로 도는 구간만**으로 계산
3. **정상 기준** (`models.SegmentBaseline`): 로봇마다 처음 5분의 평균·표준편차 → 이후 1초를 "평소보다 몇 배 벗어났나"(z)로 바꿈
4. **이상 점수**:
   - 오토인코더: 정상 z만으로 학습한 신경망(47→24→6→24→47)이 복원하지 못한 정도
   - 바퀴 이상 점수: 네 바퀴 중 **한 바퀴만 외톨이처럼** 벗어난 정도 (네 바퀴가 함께 흔들리는 바닥 영향은 작게 나옴)
   - 랜덤포레스트 이상 점수 (11/18, 고장 라벨이 있을 때): '정상이 아닐 확률'. 학습한 고장을 빠르게 잡음 (원인 분류와 같은 설정의 별도 모델)
   - 점수들을 각각 "학습에 안 쓴 정상 로봇의 99.5% = 3점, 고장 정도 0.75~0.85 = 9점" 눈금에 맞춘 뒤 **가장 큰 값**이 건강 점수 (주 모델 = 오토인코더 · 랜덤포레스트 · 바퀴 점수 중 큰 값. 고장 라벨이 없으면 오토인코더 · 바퀴 점수만)
   - 비교용 모델 3개(z-score, ECOD, PCA)도 함께 학습해 교차검증 비교표·`fig_auc.png`에만 나옴 (판정에는 안 씀). Isolation Forest는 가상 시험에서 늘 가장 낮아 11/11에 뺐음 (그 전에 학습한 모델 파일은 다시 학습해야 열림)
5. **판정** (`infer.py`): 1분마다 1초 점수의 상위 25% 지점 → 경미 경보 점수(`CAUTION_ALARM` = 2점) 미만 정상, 6점 미만 경미, 그 이상 심각. **2번 연속**일 때 상태 변경(9점 이상은 바로). 11/19 검증으로 고른 값 ([final.md](../final.md))
6. **원인**: 경미 이상일 때 랜덤포레스트가 고장 종류·바퀴 확률을 내고(최근 3분 = 180창 평균, `CAUSE_WINDOW`), **종류마다 바퀴 4개의 확률을 더해 종류를 먼저 고른 뒤** 그 종류에서 가장 높은 바퀴를 붙임(`CAUSE_BY_KIND`, 11/19: 원인 맞음 94.1% → 97.4%). SHAP으로 판단 근거 3개
7. **전류·배터리** (`power.py`): AI와 별도. 처음 5분 대비 전류가 높은 상태가 2분 연속이면 '전류 높음', 7.0 V 아래면 '배터리 낮음', 사용량 mAh

> **11/17: 칼만 필터(정지 위험까지 남은 시간 예측)를 뺐습니다.** 화면·진단 표·평가 요약에서 '정지 위험까지(분)'·'빠르면(분)'·남은 시간 오차 칸이 없어졌고, `config.KALMAN`·`KALMAN_GRID`·`TREND_PERIODS`도 지웠습니다. 판정은 지금의 건강 점수 → 고장 위험도 %·단계·원인으로만 합니다. 예전에 학습한 모델 파일도 그대로 열립니다(남은 칼만 값은 쓰지 않음).

### 7-2. 어떻게 튜닝해서 올라갔나

| 단계 | 바꾼 것 | 정답률 | 비고 |
|---|---|---|---|
| 0 | 진동만 (특징 36개) | 82.2% | 가벼운 시험 |
| 1 | 엔코더 바퀴 특징 추가 | 73.3% ↓ | 멈추거나 출발할 때 0 근처 속도로 나눠 값이 튐 → 정상도 이상처럼 보임 |
| 2 | **바퀴가 도는 구간만** 계산 | 86.7% | 가벼운 시험 |
| 3 | (2번을 시험 ①에서 측정) | **80.0%** | 시험 ① 개선 전 |
| 4 | **바퀴 상대 속도** + **바퀴 이상 점수**(큰 쪽 사용) | 91.1% | 개발용 · 바닥 오경보 2/2 |
| 5 | 가장 튄 바퀴 − 네 바퀴 중앙값 | 93.3% | 개발용 · 바닥 오경보 1/2 |
| 6 | 네 바퀴 흩어짐으로 나눔 (외톨이 점수) | 93.3% | 개발용 · 최종 |
| 7 | 6번을 시험 ①에 **한 번만** | **91.1%** | 시험 ① 개선 후 (고장 감지 67.9% → 89.3%) |

효과가 없거나 나빴던 것: 학습 로봇 4배(+1%p), 1분 점수 상위 25% 지점(오경보 증가), 오토인코더 3개 평균·튀는 값 빼기·보정 로봇 고루 섞기(오경보는 0%가 됐지만 정답률 80%로 하락 → 끔).

**왜 올라갔나:** 데이터·모델을 키운 것이 아니라, **"바퀴 고장은 한 바퀴에만 생기고, 주행 상태·바닥은 네 바퀴 모두에 영향을 준다"**는 차이를 점수로 만든 것이 핵심입니다.
- 바퀴 속도 자체는 주행·정지·회전에 따라 크게 변함 → **상대 속도**로 주행 영향을 지움
- 오토인코더는 47개 특징을 평균 내서 바퀴 하나의 이상이 묻힘 → **바퀴 이상 점수**를 따로 봄
- 바닥이 거칠면 네 바퀴가 함께 흔들림 → **외톨이 점수**로 공통 흔들림을 지움

**과대적합 방지:** 개발용 가상 로봇(seed 3001)으로만 고르고, 처음 보는 시험 로봇에는 한 번만 돌렸습니다. 개발용 93.3% ↔ 시험 91.1%로 비슷합니다.

### 7-3. 왜 가상에서는 성능이 좋게 나왔나 (실측은 더 낮을 가능성이 큼)

| 가상 데이터 | 실측에서 |
|---|---|
| 고장이 바퀴 속도·진동에 주는 영향을 **사람이 식으로 정함** (베어링 15% 느려짐 등) | 실제 고장이 엔코더에 그만큼 드러나는지 모름 |
| 정상 로봇이 얌전함 (잡음이 일정) | 바닥·배터리·온도·미끄러짐으로 정상 점수가 더 흔들림 → 오경보 또는 놓침 증가 |
| 로봇 수십 대 | 차체 1대 (교차검증이 좋게 나와도 다른 로봇에 통한다는 증거는 아님) |
| 고장 정도 라벨이 정확 | 사람이 정하는 값이라 흔들림 → 9점 눈금 부정확 |
| 엔코더 깨끗 | 해상도·빠진 펄스·미끄러짐 |

그래도 "고장 난 바퀴는 다른 바퀴와 다르게 돈다"는 원리는 실제 물리 현상이라 **엔코더를 쓰는 방향은 실측에서도 도움이 될 가능성이 높습니다.** 얼마나인지는 실측 교차검증으로만 알 수 있습니다.

### 7-4. 오토인코더 + 랜덤포레스트 vs 랜덤포레스트만 (11/18, `가상테스트/compare_ae_rf.py`)

이상을 알아채는 점수만 바꾸고(원인 분류·1분 판정·2번 연속은 같음, 11/18 전 판정 설정) 가상 시험 로봇 50대로 비교. '랜덤포레스트만'은 랜덤포레스트의 (1 - 정상 확률)을 같은 3·6·9점 눈금에 맞춘 것. 결과 표: `가상테스트_결과/AE_RF_비교*/README.md` (GitHub에 없음)

| 방법 | 모든 고장으로 학습: 정답률 / 오경보 | 마찰 증가를 학습에서 뺐을 때: 그 고장 감지 |
|---|---|---|
| 오토인코더 + 바퀴 점수 + 랜덤포레스트 (11/18 전) | 80% / 9.5% | **10대 중 10대** |
| 오토인코더 + 랜덤포레스트 | 72% / 0% | 10대 중 8대 |
| 랜덤포레스트만 | **96% / 0%** | 10대 중 4대 |
| 랜덤포레스트 + 바퀴 점수 | 92% / 9.5% | 10대 중 10대 |

- 학습에 있는 고장은 랜덤포레스트만이 가장 잘 잡음 (고장 모양을 직접 배우므로)
- 학습에 없는 고장은 랜덤포레스트만이 60%를 놓침. 오토인코더는 '평소와 다르다'로 잡음 → 고장 데이터가 적거나 없는 실측(지금 정상 40개뿐)에서는 오토인코더가 필요하고, 랜덤포레스트만으로는 학습 자체가 안 됨
- 지금 구조의 오경보 9.5%(정상 21대 중 2대)는 바퀴 이상 점수가 바닥 바뀜·짐 실음에 반응한 것

### 7-5. 실측 고장(테이프)을 바탕으로 만든 가상 로봇 시험 (11/18, `가상테스트/실측기반_시험.py`)

실측 고장 기록은 20초짜리뿐이라, 실측 조각을 이어 붙여 '처음 6분 정상 → 6~12분 고장' 가상 로봇을 만들어 시험함. 정상 = 욧골(11.15) 속도 5 기록 7개, 고장 = 욧골 앞 오른쪽 바퀴에 테이프를 감은 속도 5 기록 3개 (바퀴 불균형·변형). 고장 정도 a < 1은 정상 조각과 섞어 만듦(√(1-a)·정상 + √a·고장). **겹마다 시험 로봇은 학습에 안 쓴 실측 파일로만** 만듦 (고장 원본 2개를 번갈아 시험용으로 뺌). 겹마다 학습 24대 · 시험 45대

| 시험 로봇 | 경보(경미 이상) | 최고 점수 (중앙값) |
|---|---|---|
| 정상 30대 | 오경보 0% | 0.5~0.6점 (최대 0.84) |
| 고장 정도 1.0 (실측 그대로) 20대 | **55%** (겹1 10% · 겹2 100%), 평균 2.1분 만에 | 2.6점 · 6.7점 |

- 점수로는 **모든 고장 로봇이 모든 정상 로봇보다 높았음** (가장 약한 고장 1.3점 > 가장 높은 정상 0.84점). 놓친 것은 경미 기준 3점(정상 1초 창의 99.5% 지점)을 못 넘었기 때문

- 기준을 이 결과에 맞춰 낮추지 않음: 여기 정상은 한 날·한 바닥 기록뿐이라, 바닥만 바뀌어도 진동이 1.6~1.9배 커지는 실측에서는 오경보가 늘 수 있음. 여러 조건의 정상 기록이 늘면 다시 볼 값

### 7-6. 실측으로 보정한 가상 로봇 (엔코더 4개·각속도 포함) — 학습 → 검증으로 설정 고르기 → 처음 보는 시험 로봇 (11/18)

실측 기록으로는 모든 고장·센서를 잴 수 없어서(엔코더 1개, 각속도 없음, 고장은 테이프 불균형뿐), **실측을 바탕으로 가상 데이터를 만들어** 시험함.
- 생성기 `가상테스트/실측보정_로봇.py`: 가속도·전류·전압 = 실측 정상 조각(공3옥상 속도 5·7, 욧골 속도 5), 정지 = 실측 정지 조각. 각속도는 실측 가속도에서, 엔코더 4개는 바퀴 회전(속도 5에서 2.25 Hz)으로 만듦. **바퀴 불균형 = 실측 '테이프 고장 − 정상' 진동 증가분**(바퀴 1·2·3배 회전 성분은 회전 위상에 맞춘 사인파 + 나머지는 같은 주파수 모양의 잡음), 고장 바퀴 엔코더 ±12% 흔들림(실측 앞 오른쪽 엔코더 흔들림 2~4배와 맞음). 체결 풀림·마찰 증가는 실측이 없어 모양은 sim_robots를 쓰고 진동 증가 에너지를 실측 불균형과 같게 맞춤(가정). 헷갈리는 정상: 바닥 바뀜(실측 공3옥상 → 실측 욧골), 짐 실음, 저전압, 속도 바뀜
- 보정 확인 (가상 / 실측, 앞뒤·위아래 흔들림 RMS): 공3옥상 정상 0.19/0.21 g · 0.54/0.55 g, 욧골 정상 0.33/0.34 · 0.85/0.89, 욧골 테이프 고장 0.57/0.56 · 1.08/1.11
- 시험 `가상테스트/실측보정_시험.py --scale 0.6` (`--jobs 8`이면 실제 진단 채점을 8개 프로세스로 나눠 약 2분, 없으면 설정 하나에 18분 이상): 실측 파일을 학습 40 · 검증 14 · 시험 19개로 나눠 각 로봇은 자기 몫의 조각으로만 만듦. 학습 51대 → 검증 61대로 '이상 점수 방법 6 × 주기 점수 지점 × 연속 주기 × 경미 기준' 108조합 중 최고(오경보 5% 이하) 선택 → **처음 보는 시험 로봇 61대**(고장 38 · 정상 23)를 실제 진단 코드(`workflow.diagnose`)로 채점

## 8. 주의할 점

- **결과를 보고 설정을 여러 번 바꾸지 말 것** (과대적합). 시연용 기록은 마지막에 한 번만
- 발표에는 **실측 교차검증 수치만**. 가상 수치는 코드 점검용
- 엔코더로 학습한 모델은 진단할 기록에도 엔코더 4개가 있어야 함 (없으면 알려 줌)
- `check`의 **엔코더 상태**: '죽음'이면 그 엔코더를 빼고(4개 미만이면 진동만으로 진단), '도중에 멈춤'이면 선 빠짐 의심 → 바퀴 고장이 아니라 센서 이상일 수 있음
- 배터리 A/B를 정상·고장 기록에 골고루. 같은 로봇 이름으로 배터리를 바꿔 이어 기록하면 mAh가 이어서 더해짐
- 가상 시험(코드 점검, 성능 아님, 결과는 `가상테스트_결과/README.md`):
  - 빠른 확인 약 4분: `python 가상테스트/test_complex.py --scale 0.1`
  - 학습 약 10분 + 시험 약 10분: `python 가상테스트/test_complex.py --train-scale 0.8 --test-scale 0.75` (가상 기록 만들기 약 7분 별도. VS Code 목록에도 있음. 이 컴퓨터 실측: 0.45·0.5일 때 학습 5.6분·시험 6.5분)
  - `--train-scale`·`--test-scale`로 학습·시험 로봇 수를 따로 정함 (시험 로봇은 학습과 다른 seed로 만들어 겹치지 않음)
- 외부 데이터 시험(동작 확인, 우리 로봇 성능 아님): 회전기계 테스트베드(6 kHz, 센서 2개, 정상·축 불평형·기어 이 빠짐)를 로봇 13대 CSV로 늘려 맞춘 것
  - 만들기: `python 외부데이터_시험/만들기.py` (원본 폴더가 다르면 `--src 폴더`) → `외부데이터_시험/data/*.csv.gz`
  - 실행: VS Code 목록 **외부 데이터 시험 1 → 2 → 3** (= `python run.py check|train|diagnose --path 외부데이터_시험/data`)
  - 결과는 실측과 같은 `reports/`·`artifacts/`에 덮어씀 → 실측 CSV로 다시 `train`하면 실측 결과로 바뀜
  - 맞춘 방법(정상 6분 + 고장 단계별 이어 붙이기, 로봇마다 빠르기 0.97~1.03배·크기 0.9~1.1배, 센서 2개로 6축 채우기, 6 kHz → 1 kHz)과 한계(정상 기록 10개를 여러 로봇이 다시 씀)는 `만들기.py` 맨 위 설명
  - 처음 정상 주행 시간 비교: `만들기.py --normal-first 4 --out 외부데이터_시험/data_정상4분` (3분도 같은 방식) → `python 외부데이터_시험/기준시간_비교.py` (약 15분, 결과 `가상테스트_결과/기준시간_비교.md`)
    - 11/11 결과: 정상 6분(기준 5분)·4분(기준 3분)·3분(기준 2분) 모두 로봇 단위 결과가 같음 (정답률 76.9%, 감지 6/9, 오경보 0/4). 정상 3분인데 기준 5분을 그대로 두면 공통 기준(reference)으로 바뀌고 원인 분류가 91.8% → 84.0%로 떨어짐
